Resumo

O método copia a regra, símbolo por símbolo.

Descida recursiva é o analisador sintático escrito à mão: uma classe com a lista de tokens, o token corrente, o comparar e um método por não terminal. O passo seguinte, anunciado no fim dos slides de 12/11, é cada método devolver o seu pedaço da árvore sintática abstrata.

  • Não terminal vira método; terminal vira comparar('TIPO') (o match), que confere o token corrente e avança, ou lança "Erro sintático: esperava X, mas obtive Y".
  • | vira um if sobre self.tokenCorrente, sem consumir. Alternativa vazia é não fazer nada. Repetição vira recursão (lista_atribuicao chama a si mesma) ou while.
  • analisar() chama o método da variável inicial e termina com comparar('EOF'). As chamadas de função fazem o papel da pilha do autômato de pilha.
  • Para gerar a AST, cada token leva o lexema, comparar devolve o lexema e cada método devolve o seu nó, como ('=', 'x', 5). Chaves, ; e parênteses somem: a forma da árvore já guarda a precedência.
  • Recursão à esquerda trava a descida (a função chama a si mesma sem consumir). Precedência sai de um método por nível; associatividade à esquerda, de um while.
  • Mensagem de erro boa diz o que esperava, o que encontrou, a linha e a coluna. No modo pânico, o analisador descarta tokens até um ponto seguro e continua.
  • O exemplo de brinquedo dos slides, S(cadeia, pos), aceita bb: ele imprime o primeiro símbolo sem conferir que é a. A versão em classe começa com comparar("a") e recusa.
  • Sem comparar('EOF') no fim, o analisador aceita um começo certo e ignora o lixo do final.
  • Em <lista_atribuicao> ::= <atribuicao> <lista_atribuicao> | ε, o ε não tem else de erro: se o token não é ID, o método só volta.
  • Trocar E → E − T por E → T − E tira a recursão à esquerda e muda a conta: 5 − 3 − 1 vira 5 − (3 − 1) = 3.

Os exemplos e a dinâmica de 12/11, resolvidos

Só o token corrente decide; os outros esperam na lista.

Na aula de 12/11, o analisador é uma classe Python que recebe a lista de tipos de token e tem um método por não terminal. Aqui estão os dois exemplos dos slides, a dinâmica resolvida e a mesma classe devolvendo a árvore, que é o passo anunciado para depois.

  • O padrão é o das seções seguintes (uma função por regra, match, decisão pelo próximo token), com os nomes do professor: tokenCorrente é o token atual, comparar é o match e proximoToken() avança uma posição.
  • O construtor guarda a lista, começa em posicao = -1 e chama proximoToken(), para o tokenCorrente já ser o primeiro token.
  • proximoToken() não passa do último token. No esqueleto do exemplo 2 ele fica parado no EOF; no da dinâmica, depois do último vira None.
  • Os tokens dos slides são só tipos ('ID', 'INT'). Dá para conferir a sintaxe, mas a árvore não teria o nome da variável nem o valor. Para a árvore, cada token vira o par (tipo, lexema).
  • Os exemplos 1 e 2 são dos slides. A solução da dinâmica e a versão com árvore são autorais, testadas com Python 3.13.
# Exemplo 1 (slides): S -> aSb | ab
def analisar(self):              # supõe que o último token é sempre EOF
    self.S()
    self.comparar('EOF')

def S(self):
    self.comparar("a")
    if self.tokenCorrente == "a":   # aSb: vem outro S antes do b
        self.S()
    self.comparar("b")

# Exemplo 2 (slides): S -> aAb,  A -> c d A e | f
def S(self):
    self.comparar("a")
    self.A()
    self.comparar("b")

def A(self):
    if self.tokenCorrente == 'c':   # a alternativa que começa com c
        self.comparar('c')
        self.comparar('d')
        self.A()
        self.comparar('e')
    else:                           # senão, só pode ser f
        self.comparar('f')

# Dinâmica (solução autoral)
# <bloco>            ::= ABREBLOCO <lista_atribuicao> FECHABLOCO
# <lista_atribuicao> ::= <atribuicao> <lista_atribuicao> | ε
# <atribuicao>       ::= ID ASSIGN (ID | INT) SEMICOLON
def analisar(self):
    self.bloco()
    self.comparar('EOF')
    print("Aceita!")

def bloco(self):
    self.comparar('ABREBLOCO')
    self.lista_atribuicao()
    self.comparar('FECHABLOCO')

def lista_atribuicao(self):
    if self.tokenCorrente == 'ID':  # só uma atribuição começa com ID
        self.atribuicao()
        self.lista_atribuicao()
    # outro token: escolhe ε e volta sem consumir

def atribuicao(self):
    self.comparar('ID')
    self.comparar('ASSIGN')
    if self.tokenCorrente == 'ID':
        self.comparar('ID')
    else:
        self.comparar('INT')
    self.comparar('SEMICOLON')

# A mesma dinâmica devolvendo a árvore (autoral): tokens viram (tipo, lexema)
def comparar(self, tipoEsperado):
    tipo, lexema = self.tokenCorrente or ('EOF', '')
    if tipo != tipoEsperado:
        raise Exception(f"Erro sintático: esperava '{tipoEsperado}', mas obtive '{tipo}'")
    self.proximoToken()
    return lexema                   # quem chamou guarda o nome ou o valor

def bloco(self):
    self.comparar('ABREBLOCO')      # a chave não vira nó
    atribuicoes = self.lista_atribuicao()
    self.comparar('FECHABLOCO')
    return ('bloco', atribuicoes)

def lista_atribuicao(self):
    if self.tokenCorrente and self.tokenCorrente[0] == 'ID':
        primeira = self.atribuicao()
        return [primeira] + self.lista_atribuicao()
    return []                       # ε vira lista vazia

def atribuicao(self):
    nome = self.comparar('ID')
    self.comparar('ASSIGN')         # = e ; não viram nó
    if self.tokenCorrente[0] == 'ID':
        valor = self.comparar('ID')
    else:
        valor = int(self.comparar('INT'))
    self.comparar('SEMICOLON')
    return ('=', nome, valor)
  • Teste válido da dinâmica, { x = 5; y = x; } em tipos: imprime "Aceita!". Na versão com árvore, analisar devolve ('bloco', [('=', 'x', 5), ('=', 'y', 'x')]).
  • Teste inválido, sem o ;: depois do INT, atribuicao pede SEMICOLON e encontra FECHABLOCO. Sai "Erro sintático: esperava 'SEMICOLON', mas obtive 'FECHABLOCO'".
  • { } é aceito: lista_atribuicao vê FECHABLOCO, escolhe ε e volta. { } x só é recusado pelo comparar('EOF'): "esperava 'EOF', mas obtive 'ID'".
  • Árvore sintática × AST, com o (2+3)*4 dos slides: a árvore sintática tem um nó para cada símbolo e cada variável usada, parênteses incluídos; a AST fica só com *, tendo + (com 2 e 3) e 4 como filhos. O + embaixo já diz que ele é calculado antes. O conceito está na aula 09 e a montagem durante a descida, em Montando a árvore.
  • O exemplo de brinquedo S(cadeia, pos) dos slides aceita bb e quebra com IndexError em aab: ele não confere o primeiro símbolo e lê fora da cadeia. É a razão de existir o comparar.
  • Com if ID … else comparar('INT'), a entrada x = ; dá "esperava 'INT'", e o certo seria "esperava ID ou INT". Para a mensagem completa, teste os dois e lance o erro no else.
  • No esqueleto da dinâmica, numa lista sem 'EOF' no fim, o tokenCorrente vira None e a mensagem fica "obtive 'None'".

Uma função por regra

Cada forma do grafo vira uma linha de código.

Na descida recursiva, cada variável da gramática vira uma função com o mesmo nome, e o corpo da função copia o lado direito da regra, símbolo por símbolo, da esquerda para a direita. Para analisar um programa, você chama a função da variável inicial.

Base O que já está no caderno
  • O analisador sintático recebe os tokens do léxico, um por vez, e é a segunda das fases do compilador. O papel dele está na aula 11. Os primeiros vídeos das três playlists repetem o que é compilador e quais são as fases: é o conteúdo da aula 07.
  • A aula 08 já esboçou a ideia com fator() e termo() (descida recursiva). Aqui ela vira um analisador inteiro.
  • Descendente quer dizer que a árvore é montada da raiz para as folhas; a comparação com o ascendente está na aula 11.
  • As regras desta aula usam a EBNF da aula 09: { x } repete, [ x ] é opcional, maiúsculas são tipos de token. O Crafting Interpreters escreve x*, x+ e x?, como nas expressões regulares.
  • Regra, produção, terminal e variável (não terminal) são os da aula 01. Na gramática léxica, o alfabeto são caracteres e cada palavra é um lexema; na sintática, o alfabeto são tokens e cada palavra é um programa (ou uma expressão). O léxico implementa a primeira; o parser, a segunda.
  • Terminal no corpo: confira se o próximo token é dele e consuma (match). Diferente, é erro de sintaxe.
  • Variável no corpo: chame a função dela. Quando ela voltar, os tokens que ela gera já foram consumidos.
  • Regra com alternativas: um if (ou switch) que olha o próximo token e escolhe o caminho (decisão).
  • "Recursiva" porque uma regra que cita a si mesma, direta ou indiretamente, vira uma função que chama a si mesma. Em fator → ( expr ), fator chama expr, que acaba chamando fator de novo.
  • Terminou a função inicial sem erro e a entrada acabou: o programa está sintaticamente certo. A sequência de chamadas é a árvore (pilha de chamadas).
  • O Isidro desenha antes um grafo sintático por regra: elipse para terminal, retângulo para variável, ramos para alternativas e um caminho que volta para repetição. Depois traduz o grafo para código, como se faz com autômato e expressão regular no léxico.
  • O Lucrédio cola a gramática como comentário no código e traduz regra por regra. Ele chama o processo de sistemático e quase automático.
  • Há muitas outras técnicas de parsing (LL(k), LR(1), LALR, Earley, shunting yard, packrat, combinadores de parser). O Crafting escolhe a descida recursiva para o primeiro interpretador porque basta código escrito à mão.
  • É o jeito mais simples de escrever um parser e não depende de ferramenta. Segundo o Crafting Interpreters, o GCC, o V8 (o motor de JavaScript do Chrome) e o Roslyn (o compilador de C#) usam descida recursiva.
terminal t → match(t)
variável A → A()
α | β → if / switch pelo próximo token
{ α } → while
[ α ] → if
  • α e β são pedaços quaisquer do lado direito de uma regra. A tabela é a do Crafting Interpreters, cap. 6; o Judson diz o mesmo com outras palavras: "as funções imitam o corpo de uma produção".
  • Na linguagem Alguma do Lucrédio, programa : ':' 'DECLARACOES' listaDeclaracoes ':' 'ALGORITMO' listaComandos vira seis linhas: match, match, chamada, match, match, chamada. A regra não tem alternativa, então não há nada para decidir.
  • No exemplo do Isidro, S → a A d, A → c A | e B, B → f | g viram três procedimentos. S pede um token; se é a, chama A; na volta exige d. A consome c e chama A de novo, ou consome e e chama B. Qualquer outro token é erro.
  • Esquecer que a função da variável consome tokens. Depois de expr(), o próximo token já é o que vem depois da expressão inteira.

match e o token atual

Só o token atual decide; o resto espera.

O analisador guarda o token atual, o próximo ainda não consumido. A função match(tipo) confere se ele é do tipo esperado: se é, consome e passa ao seguinte; se não é, acusa erro de sintaxe.

  • Olhar o token atual sem consumir é espiar o lookahead. É com ele que o código escolhe a alternativa.
  • Judson: match(t) faz lookahead = próximo terminal se t é igual ao lookahead, senão erro. O lookahead pode ser variável global ou atributo da classe do analisador.
  • Lucrédio monta dois métodos: match(tipo) e lookahead(k), que espia o k-ésimo token à frente sem consumir. Por baixo, um buffer guarda até 10 tokens pedidos ao léxico com proximoToken().
  • Isidro não tem match: cada método pede scanner.nextToken() quando precisa e confere o tipo ali mesmo. Funciona, mas a regra "quem consome" fica espalhada pelo código.
  • No começo, o analisador lê o primeiro token antes de chamar a função inicial. Na versão do Judson sem léxico, cada caractere é um token e o match chama cin.get(); com léxico, o match pede o próximo token a ele, e os dois andam juntos.
  • Se você precisa do lexema depois de consumir, guarde antes ou use o que o match devolve. O Judson guarda o dígito em t antes do match porque o match avança o lookahead.
  • Na Mini (analisador completo), atual() espia e match(tipo) confere, avança self.i e devolve o token consumido. Assim nome = self.match('IDENT').lexema confere e guarda numa linha só.
  • O Crafting Interpreters separa em check (só olha), advance (consome), match (consome se casar e devolve verdadeiro ou falso) e consume (consome ou dá erro).
  • O nome muda de autor para autor. No Crafting, match é opcional (não casou, devolve falso) e consume é o obrigatório. No Lucrédio, no Judson e nesta aula, match é o obrigatório.
  • Testar o token com um if e depois chamar match confere duas vezes. O Lucrédio faz isso de propósito: fica repetitivo, mas é sempre o mesmo padrão, e o match ainda protege contra engano.

Escolhendo a alternativa pelo próximo token

Cada alternativa começa com um token diferente.

Quando a regra tem alternativas, a função olha o token atual e escolhe a única alternativa que pode começar com ele. Se nenhuma serve e a regra não tem alternativa vazia, é erro; se tem, a função simplesmente retorna.

  • Para isso dar certo, as alternativas precisam começar com tokens diferentes. O conjunto de tokens que podem começar cada uma é o FIRST, da aula 11; FIRST disjuntos é a condição do Judson e do Isidro.
  • Alternativa vazia (ε): escolher ε é não fazer nada. A função volta sem consumir, e quem chamou continua com o mesmo token.
  • Quando escolher ε? Quando o token atual não começa nenhuma outra alternativa. O Lucrédio mostra que o token que deve aparecer ali é o que pode vir depois da variável: no caso da lista de declarações, o : de :ALGORITMO. É o FOLLOW da aula 11 aparecendo no código.
  • Sem alternativa vazia, o else final é o erro, e a mensagem pode listar o que era esperado.
  • Quando duas alternativas começam igual, há duas saídas: fatorar a regra (aula 11) ou olhar mais longe. O Lucrédio, na lista de declarações, usa lookahead(4): toda declaração tem três tokens (variável, :, tipo), então o quarto diz se vem outra.
  • No Isidro, sem token de fim, o vazio de E′ é escolhido quando o léxico devolve null.
  • A regra do se do Lucrédio tem a ambiguidade do senão pendurado (aula 08): se … então se … então … senão …. Na descida, o if de [ senao … ] consome o senao assim que o vê, então ele fica com o se mais próximo. Na Mini, as chaves evitam a dúvida.
  • Judson, inst → expr ; | if ( expr ) inst | for ( optexpr ; optexpr ; optexpr ) inst e optexpr → expr | ε, com expr fazendo papel de terminal. inst() é um switch: case expr, case if, case for, default erro. optexpr() é um if: se o atual é expr, match; senão, nada.
  • Com for ( ; expr ; expr ) expr ;, o primeiro optexpr vê ;, que não é expr, e escolhe ε. A entrada não anda.
  • Exercícios do Judson: S → + S S | − S S | a vira um switch com default erro; S → ( S ) S | ε vira if atual == '(': match('('); S(); match(')'); S() e mais nada.
  • Vídeo 6 da playlist Aulas de Computação: E → i E′, E′ → + i E′ | ε, uma gramática só de somas. E′ confere se o atual é +; se não é, retorna vazio.
  • Lucrédio, regra tipo: if atual == INT: match(INT) elif atual == REAL: match(REAL) else: erro("esperava INT ou REAL"). Com else: match(REAL), o código funcionaria, mas a mensagem diria só "esperava REAL".
  • Na Mini, comando() decide por IDENT, se, enquanto ou escreva, e [ "senao" bloco ] vira if atual == 'senao'.
  • Crafting, statement(): se o atual é print, é comando de impressão; se é {, é bloco; se não é nada conhecido, cai no comando de expressão (expressão ;). Expressão é difícil de reconhecer pelo primeiro token, então ela fica como último caso.
  • Quando um token não basta: no Crafting a atribuição é uma expressão, e em a = 1 o analisador só descobre que a é o alvo ao ver o =. O truque: analisar o lado esquerdo como expressão comum e, ao achar o =, conferir se ela é uma variável e trocar pelo nó de atribuição. a + b = c dá "Invalid assignment target", sem backtracking. Na Mini o problema não aparece: comando começando com IDENT é sempre atribuição.
  • Tratar a ausência de token como erro na regra que tem ε. Em optexpr, ver ; é o caso normal.
  • Conflito escondido: na Alguma, uma expressão relacional pode começar com ( e uma aritmética também. Com FIRST em comum, o if não sabe qual escolher. O Lucrédio tira os parênteses das relacionais da linguagem para conseguir implementar; o ANTLR resolve sozinho (ANTLR).

Preditivo ou com backtracking

Cada volta relê tokens que já tinham sido lidos.

Há dois jeitos de escolher a alternativa. A descida com backtracking tenta uma, e se der errado volta o ponteiro da entrada e tenta a próxima. O analisador preditivo olha o próximo token e já sabe qual é a certa, sem nunca voltar.

  • Judson (aula 21) dá o algoritmo geral: escolha uma regra A → X₁…Xₖ; para cada Xᵢ, chame se é variável, compare e avance se é terminal. Uma falha não para tudo: volta e tenta a próxima regra. Erro só quando nenhuma serve. Por isso a função guarda onde a entrada estava quando começou.
  • Isidro compara com um robô num labirinto: tentativa e erro. Num exemplo do livro do Louden, reconhecer a*b com backtracking leva 37 passos. Em outro exemplo, com uma gramática em que cada alternativa começa por um token diferente, a versão preditiva reconhece + a * b a em menos de 12.
  • O preditivo é um caso particular da descida recursiva (Judson, aula 04): o que muda é como a alternativa é escolhida. "Se você não consegue prever, acabou o método."
  • As condições do preditivo: sem recursão à esquerda e com as alternativas começando por tokens diferentes, uma leitura da esquerda para a direita, sem voltar. O tempo cresce na proporção do número de tokens.
  • Judson mostra um caso real em que um token não basta: em C++, for ( x : c ) e for ( a ; b ; c ) começam igual. Só depois do x dá para saber qual é.
  • O ANTLR usa uma técnica que espia à frente só quando precisa (ALL(*)), e o Lucrédio diz que na maioria dos casos ela não precisa voltar.
  • Judson, aula 21: S → c A d, A → a b | a, entrada cad. O c casa; para A, tenta a b: o a casa, o b não (vem d). A entrada volta para antes do a, A tenta a, depois o d casa. A Figura 1 mostra cada passo.
  • A mesma linguagem num preditivo: fatore A → a A′, A′ → b | ε. Agora A consome o a e A′ olha o próximo: b ou qualquer outra coisa (ε).
  • Backtracking dá a resposta certa; o problema é o custo. Numa gramática grande, cada falha refaz trabalho, e o pior caso cresce muito.
  • Backtracking nesta aula é voltar na lista de tokens. O retroceder da aula 07 devolve um caractere ao léxico: outra coisa.

Recursão à esquerda, recursão de cauda e o while

Em cima, a pilha enche; embaixo, cada volta consome um +.

Uma regra com recursão à esquerda, como expr → expr + termo, vira uma função cuja primeira linha chama a si mesma sem consumir token: ela nunca sai do lugar. Por isso a gramática é reescrita sem recursão à esquerda, e a repetição que sobra vira um while.

  • Lucrédio: mesmo decidindo certo, expressaoAritmetica() chama expressaoAritmetica(), que faz a mesma pergunta e recebe a mesma resposta: laço infinito. Isidro: "você vai ter um stack overflow".
  • A transformação da gramática está na aula 11: E → E + T | T vira E → T E′, E′ → + T E′ | ε. A linguagem é a mesma.
  • No código, E′ termina chamando a si mesma: é recursão de cauda. Judson troca essa chamada por um while e, como só E chama E′, cola o laço dentro de E (um inline feito à mão). Num compilador, ele diz, desempenho vem antes.
  • Com EBNF você pula a volta: E = T { + T } já diz "um T e depois zero ou mais + T", que é um while direto. É a forma do Crafting Interpreters e da Mini.
  • Lucrédio, no ANTLR, troca a lista recursiva listaComandos : comando listaComandos | comando por comando+, e o código gerado passa a ter um laço no lugar da recursão, mais eficiente.
  • Recursão em outro lugar não atrapalha. fator → ( expr ) chama expr só depois de consumir o (, então sempre anda.
{ α } → while atual pode começar α: α
[ α ] → if atual pode começar α: α
α + → α; while atual pode começar α: α
  • α + é "uma ou mais vezes", a notação do ANTLR. Na EBNF da aula 09 ela se escreve α { α }.
  • Judson, aula 05: expr → term oper, oper → + term {print('+')} oper | − term {print('−')} oper | ε. A função final é term(); while true: if '+': match; term(); print('+') elif '−': … else return.
  • Isidro, aula 6: E → T E′, E′ → OP T E′ | ε, T → id | num e OP → + | − | * | /. E′ continua recursiva no código: OP(); T(); El().
  • Lucrédio, aritmética: depois de fatorar e tirar a recursão, ficam expressaoAritmetica, expressaoAritmetica2 (com o vazio) e uma sub-regra para + termo ou − termo. Três funções para uma regra.
  • Recursão à direita resolve o laço infinito, mas não é só uma questão de código: a árvore muda, e a associatividade pode mudar junto (próxima seção).
  • Descida recursiva muito funda pode estourar a pilha mesmo sem recursão à esquerda. Para isso existe o preditivo com tabela e pilha própria (aula 11).

Precedência e associatividade no código

em loop2 − 1 − 1: a cada volta do while, a árvore que existe vira o filho da esquerda.

Cada nível de precedência vira uma função, e a de nível mais baixo chama a do nível de cima: quem é chamado mais fundo fica mais embaixo na árvore e é calculado primeiro. A associatividade sai de como a função repete: com while, à esquerda; com recursão à direita, à direita.

  • A gramática já precisa ter os níveis da aula 08. O Lucrédio escreve a dele assim de propósito: + e − num nível, * e / no de cima.
  • O Crafting começa com uma gramática ambígua, binary → expression operator expression, em que 6 / 3 − 1 tem duas árvores, e resolve como a aula 08: uma regra por nível de precedência.
  • No Crafting, a escada é expression → equality → comparison → term → factor → unary → primary. Cada regra só casa expressões do seu nível ou de cima.
  • À esquerda: esq = termo(); while atual == '−': esq = ('−', esq, termo()). A árvore que já existe vira o filho da esquerda, então 2 − 1 − 1 é (2 − 1) − 1.
  • À direita: a função chama a si mesma para o lado direito. No Crafting, assignment → IDENT "=" assignment | equality, e a = b = c é a = (b = c). O menos unário, unary → ( "!" | "−" ) unary | primary, também.
  • Com a gramática transformada E → T E′, a árvore da gramática pende para a direita, mas o código pode montar a conta para a esquerda. O tradutor do Judson imprime 9 5 − 2 + para 9 − 5 + 2, que é (9 − 5) + 2.
soma = termo { OPSOMA termo }
termo = fator { OPMUL fator }
fator = ( expr ) | IDENT | INTEIRO
  • Os três níveis da Mini (aula 09). OPSOMA é + ou −; OPMUL é * ou /.
  • 2 + 3 * y: soma chama termo, que devolve 2; vê +, chama termo de novo, e esse termo engole 3 * y inteiro antes de voltar. Resultado: (+ 2 (* 3 y)).
  • (2 + 3) * y: o parêntese faz fator chamar expr lá de cima. Resultado: (* (+ 2 3) y).
  • Precedência do Crafting, do mais baixo ao mais alto: == !=, > >= < <=, − +, / *, e os unários ! −. Todos à esquerda, menos os unários.
  • O Isidro troca E → E op T por E → T op E para tirar a recursão à esquerda. A linguagem é a mesma, mas a árvore de 5 − 3 − 1 vira 5 − (3 − 1) = 3, e o certo é 1.
  • A tabela de precedência é escolha de projeto. O C pôs & e | abaixo de ==, e testar um bit exige parênteses: (x & 1) == 1. O Crafting cita isso como erro histórico copiado por várias linguagens.
  • No vídeo de implementação do Isidro, os quatro operadores ficam num nível só. Para só conferir a sintaxe, serve; para calcular, 2 + 3 * 4 viraria (2 + 3) * 4.

Montando a árvore durante a descida

Cada função devolve a subárvore da sua regra.

Cada função, além de conferir a sua regra, devolve o nó da AST correspondente. Quem chamou recebe a subárvore e a encaixa no nó dele; quando a função da variável inicial retorna, a árvore inteira está pronta.

  • A AST é a sintaxe abstrata da aula 09: só o que tem significado. Parênteses, ; e as variáveis intermediárias (termo, fator) não viram nó.
  • Judson: a sequência de chamadas já define a árvore de derivação, sem montar nada. Para a entrada do for, inst, optexpr, optexpr, optexpr, inst. Os nós podem ser criados dentro das funções quando você precisar deles.
  • Um tipo de nó por tipo de construção: no Crafting, Binary(left, operator, right), Unary(operator, right), Grouping(expression) e Literal(value) para expressões, e outra família para comandos (Print, Var, Block). As duas famílias são separadas porque, na gramática, nenhum lugar aceita expressão e comando ao mesmo tempo.
  • Os nós só guardam dados, sem comportamento: o parser cria, as fases seguintes leem. Como há várias operações sobre a mesma árvore (imprimir, conferir tipos, interpretar), cada operação fica num lugar só. Em Java, o Crafting usa o padrão Visitor; na Mini, uma função Python com um if por tipo de nó faz o mesmo papel (texto()).
  • Para conferir a precedência, imprima a árvore com todos os parênteses, no estilo Lisp: (* (- 123) (group 45.67)) no Crafting, (+ 2 (* 3 y)) na Mini. Imprimir 2 + 3 * y de volta não mostraria quem ficou em cima.
  • Calcular uma árvore é percorrê-la em pós-ordem: os filhos primeiro, depois o nó. É por isso que quem fica embaixo é calculado antes.
  • Sem AST, o analisador só responde "certo" ou "errado". É o que o Lucrédio monta à mão: passar por todas as funções sem erro prova que o programa segue a gramática, mas nenhuma árvore fica guardada.
  • Outra saída é agir durante a descida, com ações semânticas no meio da regra. A ação entra na função no mesmo lugar em que está na regra: depois de X na regra, depois da chamada de X no código.
  • No ANTLR, a ação vai entre chaves na gramática e é copiada para o parser gerado (ANTLR).
  • Mini: soma() faz esq = (op, esq, self.termo()); fator() devolve a expressão de dentro dos parênteses sem criar nó; atribuicao() devolve ('=', nome, valor). Para x = 2 + 3 * y; sai (= x (+ 2 (* 3 y))).
  • Judson, tradutor de infixa para pós-fixa: expr → expr + term {print('+')} | expr − term {print('−')} | term, term → 0 {print('0')} | … | 9 {print('9')}. Na transformação, as ações são copiadas como se fossem terminais. 9 − 5 + 2 sai 95−2+.
  • No mesmo tradutor, 2++4−3 dá erro de sintaxe no segundo +, mas a saída já tinha impresso 2 e ainda não o +: o erro parece aparecer antes do lugar real. É o mesmo efeito do ponto e vírgula esquecido que o compilador acusa na linha de baixo.
  • Ação na posição errada muda a saída. Em + term {print('+')}, o print depois de term() dá pós-fixa; antes, daria pré-fixa.
  • O Crafting guarda um nó Grouping para os parênteses; a Mini descarta, porque a forma da árvore já registra o agrupamento. As duas escolhas funcionam; o que não pode é a árvore perder a ordem das contas.

Mensagens de erro e o fim do arquivo

A mensagem sai do match que falhou.

Um erro sintático aparece quando o token atual não é nenhum dos que a função esperava naquele ponto. A mensagem útil diz o que era esperado, o que foi encontrado e em que linha e coluna. E o analisador só aceita o programa se, no fim, a entrada também acabou.

  • Lucrédio: erroSintatico(esperados…) monta "erro sintático: esperando um destes, mas foi encontrado X" e encerra o programa. O match chama essa função quando falha.
  • Isidro: uma exceção própria, IsiSyntaxException, com mensagens como "ID or Number expected, found identifier (abc)". Depois, a pedido de um aluno, ele põe linha e coluna em cada token e na mensagem. O main separa erro léxico de erro sintático.
  • Judson: throw de uma classe SyntaxError vazia e um catch no main. O Crafting faz igual e escreve "at end" quando o erro é no fim do arquivo.
  • Os tipos de erro e as estratégias de recuperação em geral estão na aula 11; aqui fica como implementar na descida recursiva.
  • Fim do arquivo: depois da função inicial, exija o token de fim. O Judson confere se sobrou algo além do \n; o Isidro, no procedimento principal, confere se chegou ao fim de arquivo.
  • No Crafting, depois de um erro sintático o parse() não entrega árvore utilizável, e as fases seguintes não rodam (hadError).
  • Num editor ou IDE, o parser roda de novo a cada tecla, sobre código pela metade. Por isso o Crafting trata a mensagem de erro como parte da interface da linguagem.
  • O Crafting lista o que o parser precisa: detectar e reportar o erro, nunca travar nem entrar em laço; e o que é bom ter: ser rápido, achar o máximo de erros diferentes e evitar erros em cascata. As duas últimas brigam, e a recuperação é o meio-termo.
  • Lucrédio põe se numero1 > numero2 < no programa e recebe "esperando ENTAO, mas foi encontrado <". Exatamente o lugar do erro.
  • Depois ele acrescenta, depois do último comando, uma variável solta, e nenhum erro aparece: a regra programa termina na lista de comandos e não diz o que vem depois. Com match(FIM) no fim de programa, sai "esperando FIM, mas foi encontrado" a variável.
  • No primeiro teste dele, o sintático acusa erro numa declaração correta. O culpado era o léxico: uma palavra-chave escrita errada, e o tipo virava variável. No ANTLR, a mesma coisa: "no viable alternative" numa linha certa, porque a regra das variáveis vinha antes da dos operadores E e OU e engolia as palavras (aula 07).
  • Na Mini, erro() registra "linha 1, coluna 9: esperava uma expressão, encontrei ';'" e devolve a exceção para quem chamou lançar.
  • Erro na linha de baixo não quer dizer código errado na linha de baixo. Quem esquece o ; só é descoberto no primeiro token da linha seguinte.
  • Antes de caçar o erro na gramática, imprima os tokens. O Lucrédio faz isso duas vezes, e nas duas o problema era do léxico.

Recuperação de erros: modo pânico e sincronização

Os tokens entre o erro e o ponto seguro são jogados fora.

Em vez de parar no primeiro erro, o analisador entra em modo pânico: registra o erro, sai das funções em que estava e descarta tokens até achar um token de sincronização, um ponto em que sabe recomeçar. Aí continua e pode achar os próximos erros.

  • Os vídeos do Lucrédio, do Isidro e do Judson param no primeiro erro. O Judson só anuncia, na aula 21, que FIRST e FOLLOW também servem para escolher os tokens de sincronização. A técnica vem do Crafting Interpreters, cap. 6 e 8.
  • Na descida recursiva, o estado do analisador são as funções em andamento na pilha de chamadas. Lançar uma exceção desempilha todas até a que vai capturar.
  • O lugar clássico para sincronizar é o comando. A função que analisa um comando (no Crafting, declaration()) envolve a análise num try; no except, chama sincronizar().
  • sincronizar() descarta tokens até passar por um ; ou até ver uma palavra que começa comando (se, enquanto, escreva; no Crafting, class, fun, var, for, if…).
  • O preço: um erro real escondido nos tokens descartados não aparece. O ganho: os erros falsos, efeito só da confusão do primeiro, também não.
  • Nem todo erro precisa de pânico. O Crafting reporta "argumentos demais" ou "Invalid assignment target" e segue analisando, porque ali o analisador não se perde. Por isso a função de erro devolve a exceção em vez de lançar: quem chama decide. A Mini faz igual (raise self.erro(…)).
  • Laços que leem até um token de fechamento também conferem o fim do arquivo: while not '}' and not EOF. Sem isso, um } esquecido trava o analisador.
  • Outra técnica, proposta como desafio no Crafting: produções de erro. A gramática ganha uma regra para um erro comum, como um operador binário sem o lado esquerdo (* 3); o analisador reconhece, reporta e consome o operando, sem entrar em pânico.
  • Mini, entrada x = 3 + ;, escreva(x y);, escreva(2);. Saem dois erros, "linha 1, coluna 9: esperava uma expressão, encontrei ';'" e "linha 2, coluna 11: esperava ')', encontrei 'y'", e a AST (programa [(escreva 2)]). A Figura 3 mostra o que é descartado.
  • Na Mini, quem captura é lista_comandos(), usada no programa e em cada bloco. Um erro dentro de um bloco sincroniza ali dentro, e o } é token de sincronização para o bloco poder fechar.
  • Se o erro foi no primeiro token do comando e a sincronização para nele mesmo, o analisador tenta o mesmo comando para sempre. Por isso a Mini descarta um token quando nada foi consumido.
  • Na Mini, IDENT não é token de sincronização porque aparece no meio das expressões. O efeito colateral: depois de um erro, uma atribuição pode ser engolida sem aviso até o próximo ;.

Um analisador completo em Python para a Mini

Um analisador descendente recursivo inteiro, autoral desta aula, para a linguagem Mini da aula 09: léxico curto, uma função por regra da EBNF, AST em tuplas, mensagens com linha e coluna e modo pânico. São cerca de 180 linhas, testadas com Python 3.13.

  • O léxico é uma versão curta do da aula 07: uma expressão regular por tipo de token, palavras-chave separadas dos identificadores e um token EOF no fim.
  • Palavra-chave e pontuação usam o próprio texto como tipo ('se', ';'), então match(';') lê como a regra.
  • Cada função de regra tem a regra em EBNF no comentário de cima.
  • A AST usa tuplas: ('=', nome, valor), ('+', esq, dir), ('se', cond, entao, senao). Nome de variável fica como texto; número, como int; verdadeiro e falso, como bool.
import re
from collections import namedtuple

# ---------- léxico: uma versão curta do analisador da aula 07 ----------
Token = namedtuple('Token', 'tipo lexema linha coluna')
PALAVRAS = {'se', 'senao', 'enquanto', 'escreva', 'verdadeiro', 'falso'}
PADRAO = re.compile(r'''(?P<ESPACO>\s+|//[^\n]*)
  |(?P<INTEIRO>\d+)  |(?P<IDENT>[a-z][a-z0-9_]*)
  |(?P<OPREL>==|!=|<=|>=|<|>)  |(?P<SIMBOLO>[=(){};])
  |(?P<OPSOMA>[+-])  |(?P<OPMUL>[*/])''', re.VERBOSE)

def lexico(fonte):
    tokens, pos, linha, inicio_linha = [], 0, 1, 0
    while pos < len(fonte):
        m = PADRAO.match(fonte, pos)
        if not m:
            raise SyntaxError(f'linha {linha}: erro léxico em {fonte[pos]!r}')
        tipo, lex = m.lastgroup, m.group()
        if (tipo == 'IDENT' and lex in PALAVRAS) or tipo == 'SIMBOLO':
            tipo = lex                     # palavra-chave e pontuação: o tipo é o próprio texto
        if tipo != 'ESPACO':
            tokens.append(Token(tipo, lex, linha, pos - inicio_linha + 1))
        for i, c in enumerate(lex):        # conta linhas para as mensagens de erro
            if c == '\n':
                linha, inicio_linha = linha + 1, pos + i + 1
        pos = m.end()
    tokens.append(Token('EOF', '', linha, pos - inicio_linha + 1))
    return tokens

# ---------- sintático: descida recursiva, uma função por regra ----------
class ErroSintatico(Exception):
    pass

INICIO_COMANDO = {'IDENT', 'se', 'enquanto', 'escreva'}

class Parser:
    def __init__(self, tokens):
        self.tokens, self.i, self.erros = tokens, 0, []

    def atual(self):                       # espia o próximo token, sem consumir
        return self.tokens[self.i]

    def match(self, tipo):                 # confere o tipo e consome
        if self.atual().tipo != tipo:
            raise self.erro(f'esperava {tipo!r}')
        self.i += 1
        return self.tokens[self.i - 1]

    def erro(self, esperado):              # registra e devolve a exceção
        tk = self.atual()
        achou = repr(tk.lexema) if tk.lexema else 'o fim do arquivo'
        self.erros.append(f'linha {tk.linha}, coluna {tk.coluna}: {esperado}, encontrei {achou}')
        return ErroSintatico()

    # programa = { comando } EOF ;
    def programa(self):
        comandos = self.lista_comandos(fim='EOF')
        self.match('EOF')
        return ('programa', comandos)

    def lista_comandos(self, fim):         # { comando } vira um while
        comandos = []
        while self.atual().tipo not in (fim, 'EOF'):
            inicio = self.i
            try:
                comandos.append(self.comando())
            except ErroSintatico:          # modo pânico
                if self.i == inicio:
                    self.i += 1            # nada foi consumido: descarta o token do erro
                self.sincronizar()
        return comandos

    def sincronizar(self):                 # descarta até depois de ';' ou até um começo seguro
        while self.atual().tipo not in ('se', 'enquanto', 'escreva', '}', 'EOF'):
            self.i += 1
            if self.tokens[self.i - 1].tipo == ';':
                return

    # comando = atribuicao | se | enquanto | escreva ;
    def comando(self):
        tipo = self.atual().tipo           # o lookahead escolhe a alternativa
        if tipo == 'IDENT':    return self.atribuicao()
        if tipo == 'se':       return self.se()
        if tipo == 'enquanto': return self.enquanto()
        if tipo == 'escreva':  return self.escreva()
        raise self.erro('esperava um comando')

    # atribuicao = IDENT "=" expr ";" ;
    def atribuicao(self):
        nome = self.match('IDENT').lexema
        self.match('=')
        valor = self.expr()
        self.match(';')
        return ('=', nome, valor)

    # se = "se" "(" expr ")" bloco [ "senao" bloco ] ;
    def se(self):
        self.match('se'); self.match('(')
        cond = self.expr()
        self.match(')')
        entao, senao = self.bloco(), None
        if self.atual().tipo == 'senao':   # [ ... ] vira um if
            self.match('senao')
            senao = self.bloco()
        return ('se', cond, entao, senao)

    # enquanto = "enquanto" "(" expr ")" bloco ;
    def enquanto(self):
        self.match('enquanto'); self.match('(')
        cond = self.expr()
        self.match(')')
        return ('enquanto', cond, self.bloco())

    # escreva = "escreva" "(" expr ")" ";" ;
    def escreva(self):
        self.match('escreva'); self.match('(')
        valor = self.expr()
        self.match(')'); self.match(';')
        return ('escreva', valor)

    # bloco = "{" { comando } "}" ;
    def bloco(self):
        self.match('{')
        comandos = self.lista_comandos(fim='}')
        self.match('}')
        return comandos

    # expr = soma [ OPREL soma ] ;
    def expr(self):
        esq = self.soma()
        if self.atual().tipo == 'OPREL':
            op = self.match('OPREL').lexema
            esq = (op, esq, self.soma())
        return esq

    # soma = termo { OPSOMA termo } ;
    def soma(self):
        esq = self.termo()
        while self.atual().tipo == 'OPSOMA':
            op = self.match('OPSOMA').lexema
            esq = (op, esq, self.termo())  # o que já existe vira o filho da esquerda
        return esq

    # termo = fator { OPMUL fator } ;
    def termo(self):
        esq = self.fator()
        while self.atual().tipo == 'OPMUL':
            op = self.match('OPMUL').lexema
            esq = (op, esq, self.fator())
        return esq

    # fator = "(" expr ")" | IDENT | INTEIRO | "verdadeiro" | "falso" ;
    def fator(self):
        tipo = self.atual().tipo
        if tipo == '(':
            self.match('(')
            dentro = self.expr()
            self.match(')')
            return dentro                  # os parênteses não viram nó
        if tipo == 'IDENT':   return self.match('IDENT').lexema
        if tipo == 'INTEIRO': return int(self.match('INTEIRO').lexema)
        if tipo in ('verdadeiro', 'falso'):
            return self.match(tipo).tipo == 'verdadeiro'
        raise self.erro('esperava uma expressão')

def texto(no):                             # AST em uma linha: (+ 2 (* 3 y))
    if isinstance(no, tuple):
        return '(' + ' '.join(texto(f) for f in no if f is not None) + ')'
    if isinstance(no, list):
        return '[' + ' '.join(texto(f) for f in no) + ']'
    if isinstance(no, bool):
        return 'verdadeiro' if no else 'falso'
    return str(no)

def analisar(fonte):
    p = Parser(lexico(fonte))
    arvore = p.programa()
    return arvore, p.erros

if __name__ == '__main__':
    arvore, erros = analisar('x = 2 + 3 * y;')
    print(texto(arvore))
    arvore, erros = analisar('x = 3 + ;\nescreva(x y);\nescreva(2);')
    print(texto(arvore))
    print('\n'.join(erros))
  • Rodando o arquivo, sai (programa [(= x (+ 2 (* 3 y)))]) para x = 2 + 3 * y;. Para a entrada com erros, sai (programa [(escreva 2)]) e as duas mensagens da recuperação.
  • O fatorial da aula 09, n = 5; f = 1; enquanto (n > 1) { f = f * n; n = n - 1; } escreva(f);, dá (programa [(= n 5) (= f 1) (enquanto (> n 1) [(= f (* f n)) (= n (- n 1))]) (escreva f)]), sem erros.
  • x = 2 @ 3; nem chega ao sintático: o léxico levanta "erro léxico em '@'".
  • escreva(1 < 2 < 3); dá erro no segundo <: em expr = soma [ OPREL soma ] a comparação aparece no máximo uma vez.
  • A gramática aceita se (1 + 2) { … }. Conferir que a condição é booleana é trabalho da semântica, como diz a especificação da Mini.

A pilha de chamadas é a árvore

Em qualquer instante, a pilha é um caminho da árvore.

Enquanto o analisador trabalha, as funções em andamento formam uma pilha: a da variável inicial embaixo, a que está consumindo tokens no topo. Em cada instante a pilha é o caminho da raiz da árvore até o nó que está sendo montado, e a ordem das chamadas percorre a árvore inteira.

  • É a pilha de execução da aula 04: cada chamada empilha um quadro com as variáveis locais e o endereço de volta. O analisador não precisa de pilha própria.
  • No vídeo 6 da playlist Aulas de Computação, o professor desenha essa pilha à mão, com a linha para onde cada chamada volta, para a entrada da gramática de somas.
  • Lucrédio: a sequência de chamadas recursivas corresponde às derivações e à árvore de análise sintática.
  • Ela também é o "estado" do analisador: em que regra ele está e o que falta da regra. É por isso que uma exceção basta para reiniciar o estado na recuperação.
  • A altura máxima da pilha acompanha a altura da árvore. Expressões muito aninhadas, como ((((1)))), empilham fundo, e é isso que pode estourar a pilha (Judson, aula 21).
  • A Figura 2 roda a Mini em x = 2 + 3 * y;. Repare que nenhum token é consumido enquanto a pilha cresce de atribuicao até fator, e que o + é consumido por soma, lá embaixo, depois que termo e fator já voltaram.

O mesmo analisador gerado pelo ANTLR

match, chamadas e um switch para decidir.

O ANTLR lê a gramática num arquivo .g4 e gera um analisador descendente recursivo: uma função por regra, match para os terminais e um switch para escolher a alternativa. A diferença é como ele decide: o ALL(*) espia à frente o quanto precisar (aula 11).

  • No vídeo 09, o Lucrédio usa a mesma gramática da Alguma do vídeo 08, agora com as regras léxicas no mesmo arquivo, e não transforma nada: o ANTLR aceita a recursão à esquerda direta e reescreve sozinho.
  • O conflito dos parênteses (expressão relacional e aritmética começando com () também deixa de ser problema: a predição adaptativa experimenta à frente até achar a alternativa certa.
  • O código gerado tem match, chamadas para as outras regras e, onde há decisão, um switch sobre adaptivePredict. Dá para depurar passo a passo como o feito à mão.
  • Recursão à esquerda indireta, passando por outra regra, o ANTLR não resolve (Lucrédio, vídeo 08).
  • Ações semânticas: código Java entre { } no meio de uma regra é copiado para o parser gerado e roda naquele ponto. $VARIAVEL.text é o texto do token; returns [String tipo] faz a regra devolver um valor; rótulos como cmd1=comando cmd2=comando separam duas ocorrências da mesma regra.
  • Ação que lê um valor antes de a regra que o produz ter sido analisada não funciona: a posição importa, como na montagem da árvore.
  • Por que aprender a versão à mão, se o ANTLR faz tudo? Para depurar: entender a chamada recursiva, o match e a decisão, que é onde costuma estar o problema. Num gerador ascendente (aula 11), regra e código não se correspondem assim, e depurar é mais difícil.
  • No main: CharStreams.fromFileName, o léxico gerado, CommonTokenStream (o buffer de tokens que o Lucrédio fez à mão) e parser.programa(), a regra inicial.
  • Para exigir o arquivo inteiro, a regra programa termina com EOF, como no manual.
  • Com listaComandos : comando+, o gerado troca a chamada recursiva por um laço.
  • O projeto usa Maven com o plugin do ANTLR 4 e o assembly para gerar um jar com as dependências; a gramática fica em src/main/antlr4/, nos diretórios do pacote.
  • Erro de digitação Java dentro de uma ação só aparece ao compilar o parser gerado, numa linha do arquivo gerado, não da gramática.

No projeto da nova linguagem

Cada passo usa uma seção desta aula.

Para o projeto, o analisador sintático da nova linguagem sai da especificação da aula 09: a gramática em EBNF vira o roteiro das funções, os tokens vêm do léxico da aula 07 e os exemplos válidos e inválidos viram testes.

  • Antes de escrever código, confira a gramática: nenhuma recursão à esquerda e, em cada regra com alternativas, tokens iniciais diferentes (aula 11). O que não passar, reescreva ou use lookahead maior onde for pontual.
  • Expressões: um nível por função, na ordem da especificação. Decida a associatividade de cada operador e confira com uma conta como 5 − 3 − 1.
  • A AST é a sintaxe abstrata da especificação. A fase seguinte, a semântica, trabalha em cima dela.
  • Decida onde cada comando pode aparecer. O Crafting separa declaration (com var) de statement: if (x) var y = 1; é proibido, porque ninguém saberia o escopo de y. Na gramática, isso é um nível de "precedência" entre comandos.
  • Defina onde sincronizar: em geral no ;, nas palavras que começam comando e no fecha-bloco.
  • Com os exemplos da especificação: cada válido tem de passar sem erro; cada um com erro sintático tem de gerar a mensagem com linha e coluna certas.
  • Depois do parser vem a semântica e, num interpretador, a execução da AST: guardar o valor das variáveis num ambiente e criar um ambiente novo para cada bloco (escopo). É a segunda metade do cap. 8 do Crafting e fica para as próximas aulas.
  • O slide da aula 01 do prof. Resina já diz que o sintático do projeto usa recursão e monta a árvore sintática (aula 08).
  • Começar pelo código e acertar a gramática depois. Cada mudança de regra muda funções e mensagens; com a gramática conferida antes, a tradução é mecânica.

Treino: exercícios autorais

Exercícios autorais, não do professor, sobre os vídeos e o analisador da Mini. Resolva antes de abrir a resposta; ela é uma solução possível, não a única.

1 · Escreva a função de lista = item { "," item } ;, com item = IDENT, devolvendo a lista de nomes.
Uma resposta

def lista(self): nomes = [self.match('IDENT').lexema]; while self.atual().tipo == ',': self.match(','); nomes.append(self.match('IDENT').lexema); return nomes. O { } virou while, e a condição é o token que começa o que se repete.

2 · A regra L → L , id | id pode virar função direto? Se não, reescreva e escreva o código.
Uma resposta

Não: L() chamaria L() na primeira linha. Reescreva L → id L′, L′ → , id L′ | ε, ou em EBNF L = id { "," id }, que é o exercício 1.

3 · Desenhe a árvore de 5 − 3 − 1 com E → T − E | T e com o while da Mini. Qual conta cada uma dá?
Uma resposta

E → T − E: o E da direita pega 3 − 1, então 5 − (3 − 1) = 3. O while da Mini: (- (- 5 3) 1) = 1, que é o certo para o menos.

4 · Acrescente à Mini o menos unário (-x, --x). Onde entra na gramática, qual a associatividade e como fica o código?
Uma resposta

Um nível acima de fator: termo = unario { OPMUL unario }, unario = "-" unario | fator. Associativo à direita, por recursão: if self.atual().lexema == '-': self.match('OPSOMA'); return ('neg', self.unario()), senão return self.fator(). Repare que o - chega como OPSOMA.

5 · Na gramática A → a b | a c | a, conte as tentativas de uma descida com backtracking para a, e escreva a versão preditiva.
Uma resposta

Tenta a b (o a casa, falta b), volta, tenta a c (falha igual), volta, tenta a: três tentativas e o a lido três vezes. Preditiva: A → a A′, A′ → b | c | ε, com A′ olhando o token depois do a.

6 · Na Mini, } ) x = 1; gera um erro só e a AST sai vazia. Por que a atribuição sumiu, e como evitar?
Uma resposta

O erro é no }. Nada foi consumido, então o } é descartado, e sincronizar() pula ) x = 1 até o ;, porque IDENT não é token de sincronização. Uma saída: parar também em IDENT quando o token seguinte for = (olhando dois à frente), que só acontece no começo de uma atribuição.

7 · Quantos quadros a pilha tem, no máximo, para x = ((1)); na Mini?
Uma resposta

programa, lista_comandos, comando, atribuicao, e então expr, soma, termo, fator três vezes (um por par de parênteses e o do 1): 4 + 3 × 4 = 16 quadros, sem contar o match.

8 · Escreva rpn(no), que transforma uma expressão da AST da Mini em notação pós-fixa ((1 + 2) * (4 - 3) vira 1 2 + 4 3 - *).
Uma resposta

def rpn(no): if isinstance(no, tuple): op, esq, dir = no; return f'{rpn(esq)} {rpn(dir)} {op}' e, para folhas, return texto(no). É um percurso em pós-ordem: os dois filhos, depois o operador. Para 9 - 5 + 2 sai 9 5 - 2 +, a mesma saída do tradutor do Judson, agora a partir da árvore.

9 · Reescreva bloco = "{" { comando } "}" sem EBNF, só com regras de GLC.
Uma resposta

B → { L }, L → C L | ε. A repetição virou uma variável nova recursiva à direita, que pode sumir. Por isso a EBNF é só uma forma mais curta.

10 · Acrescente à Mini o operador ternário c ? a : b. Em que nível de precedência ele entra, com que associatividade, e o que pode ficar entre o ? e o :?
Uma resposta

Abaixo da comparação, como em C: cond = expr [ "?" cond ":" cond ], e quem usava expr passa a usar cond. Associativo à direita, por recursão: a ? b : c ? d : e é a ? b : (c ? d : e). Entre o ? e o : cabe qualquer expressão, porque os dois tokens cercam o meio como parênteses. O código: c = self.expr(); if atual == '?': match; a = self.cond(); match(':'); b = self.cond(); return ('?', c, a, b).

11 · O ANTLR acusa "no viable alternative at input" numa linha que você jura estar certa. O que conferir primeiro?
Uma resposta

Os tokens: imprima a lista que o léxico gerou para aquela linha. Nos dois vídeos do Lucrédio, uma palavra-chave estava virando identificador (escrita errada, ou com a regra de VARIAVEL antes dela). Só depois olhe a gramática.

Uma boa resposta traz o código ou a gramática e uma linha dizendo qual token decide cada escolha.

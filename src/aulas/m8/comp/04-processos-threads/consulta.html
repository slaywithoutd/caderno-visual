O sistema operacional e o kernel

O sistema operacional (SO) é o programa que fica entre os seus programas e o hardware: Windows, Linux, macOS, Android, iOS. O kernel é a parte do SO que fica sempre carregada na memória, com acesso total ao hardware.

  • Máquina estendida: o SO esconde os detalhes do hardware atrás de serviços simples. Seu código diz "abra o arquivo notas.txt", e o SO cuida de achar os blocos certos no disco.
  • Gerente de recursos: o SO divide CPU, memória e dispositivos entre vários programas que disputam ao mesmo tempo, sem que um atrapalhe ou espione o outro.
  • O kernel gerencia processos, memória, arquivos e dispositivos. O resto do SO (janelas, utilitários, o interpretador de comandos) são programas comuns.
  • "Núcleo", em português, serve para o kernel do SO e para cada processador dentro do chip (core). Este caderno não usa "núcleo": kernel é sempre o do SO, e core é o do hardware, como em "uma CPU com 4 cores".

Modo usuário e modo kernel

A CPU tem pelo menos dois modos de operação, marcados por um bit num registrador especial. Em modo kernel ela executa qualquer instrução e acessa qualquer endereço; em modo usuário, recusa as instruções privilegiadas.

  • Por quê: se qualquer programa pudesse mandar comandos direto ao disco ou mexer na memória dos outros, um bug num jogo derrubaria a máquina inteira.
  • Modo kernel também se chama modo núcleo, supervisor ou privilegiado. Só o código do kernel roda assim; todo programa seu roda em modo usuário.
  • Instrução privilegiada: só roda em modo kernel. Exemplos: conversar com um dispositivo de E/S, mudar a tabela de páginas da memória virtual (aula 02), desligar interrupções, mudar o bit de modo.
  • Se um programa em modo usuário tenta uma instrução privilegiada, a CPU não executa: desvia para o kernel, que em geral encerra o programa.

Syscall: pedir ao kernel

Syscall (system call, chamada de sistema) é o pedido formal de um programa ao kernel. É assim que um programa que não pode falar com o disco lê um arquivo.

  • Exemplos do Linux: read (ler), write (escrever), open (abrir arquivo), fork (criar processo), exit (terminar).
  • Em geral você não chama direto: print do Python e printf do C são funções de biblioteca que, por baixo, fazem a syscall write.
  • Custa caro perto de uma função comum: trocar de modo e conferir tudo leva de centenas de ns a alguns µs.
  • O programa põe o número do serviço e os argumentos em registradores e executa uma instrução especial de trap (syscall no x86-64, svc no ARM).
  • A CPU muda para modo kernel e salta para um endereço fixo, escolhido pelo kernel. O programa não consegue pular para outro lugar do kernel.
  • O kernel confere o pedido (o arquivo existe? você tem permissão?), faz o serviço e devolve o resultado num registrador.
  • Volta para o modo usuário, na instrução seguinte.

Interrupção, temporizador e exceção

Interrupção é um aviso elétrico que um dispositivo manda para a CPU: "aconteceu algo". A CPU para o que faz, roda o tratador de interrupção no kernel e depois volta ao ponto exato onde estava.

  • E/S (entrada e saída, I/O): toda troca de dados entre a CPU e o mundo de fora da memória: disco, teclado, tela, rede, sensores. Dispositivos de E/S são lentíssimos perto da CPU; ficar perguntando "já acabou?" em loop desperdiçaria milhões de ciclos.
  • Tratador de interrupção: a rotina do kernel para aquele tipo de evento. Eventos: o disco terminou uma leitura, uma tecla foi pressionada, chegou um pacote de rede.
  • Temporizador (timer, relógio): circuito que interrompe a CPU em intervalos fixos, por exemplo a cada 1 ms. Garante ao SO retomar o controle mesmo de um programa que nunca faz syscall.
  • Exceção: a mesma ideia, mas causada pela instrução que está executando: divisão por zero, acesso a endereço proibido, instrução privilegiada em modo usuário.
  • Interrupção é assíncrona: chega a qualquer momento, sem relação com a instrução atual. Exceção é síncrona: acontece sempre no mesmo ponto se você rodar o programa de novo.
  • A syscall às vezes é chamada de "interrupção de software", porque entra no kernel pelo mesmo tipo de caminho.
  • Dois modos de operação, interrupções e temporizador: são as três ferramentas que o hardware dá ao SO.
  • A CPU termina a instrução atual.
  • Guarda o mínimo para poder voltar: o PC e o registrador de status.
  • Passa para modo kernel e executa o tratador de interrupção.
  • No fim, volta ao ponto exato onde estava.
  • Na figura abaixo, as duas coisas juntas: um processo pede uma leitura de disco por syscall, espera, e o disco avisa por interrupção.

Multiprogramação e tempo compartilhado

Multiprogramação é manter vários programas na memória ao mesmo tempo: quando um para para esperar E/S, o SO entrega a CPU a outro. Na monoprogramação (um programa na memória por vez), a CPU fica ociosa em todas as esperas.

  • Um programa típico alterna: calcula um pouco, espera E/S, calcula mais um pouco.
  • Tempo compartilhado (time-sharing): multiprogramação mais o temporizador. Cada programa recebe um quantum (uma fatia curta de CPU, assunto da aula 06), por exemplo 10 ms, e é interrompido no fim dele mesmo sem pedir E/S. Para quem está usando, tudo parece rodar ao mesmo tempo.
  • Para isso funcionar, o SO precisa parar um programa no meio e depois continuar exatamente de onde ele parou. O que o SO guarda para conseguir isso transforma um programa em processo.
  • Um programa usa 10 ms de CPU e depois espera 40 ms pelo disco, em ciclo. Sozinho, ocupa a CPU 10 ms a cada 50 ms: 10 / 50 = 20 %.
  • Com 4 programas iguais, enquanto um espera os outros usam a CPU: no melhor caso, 4 × 20 % = 80 % de uso. No pior caso as esperas coincidem e o ganho é menor.

Programa × processo

Um programa é um arquivo: instruções e dados parados no disco, esperando. Um processo é esse programa rodando, com tudo o que o SO precisa para interrompê-lo e retomá-lo sem perder nada.

  • Para Machado & Maia, o processo é o ambiente em que um programa executa, com três partes: contexto de hardware, contexto de software e espaço de endereçamento.
  • Programa: estático e passivo. Fica no disco (/usr/bin/python3, chrome.exe) e não muda enquanto não for recompilado.
  • Processo: dinâmico e ativo. Fica na memória, tem contexto, nasce, muda de estado e termina.
  • Um programa pode virar vários processos: três janelas do bloco de notas são três processos do mesmo programa, cada um com o seu texto (duas pessoas fazendo a mesma receita em cozinhas diferentes).
  • O processo é a unidade que o SO usa para dividir recursos (memória, arquivos, tempo de CPU) e para proteger: um processo não lê a memória de outro.

Programa é código parado no disco (passivo). Processo é o programa em execução, com contexto de hardware, contexto de software e espaço de endereçamento (ativo). Um programa pode dar origem a vários processos.

Contexto do processo e contexto de hardware

Contexto do processo = contexto de hardware + contexto de software; a memória é o espaço de endereçamento. O contexto de hardware é o conteúdo dos registradores da CPU no momento em que o processo para: o que ele "tinha na cabeça".

  • Registradores gerais: guardam os valores intermediários das contas.
  • Contador de programa (PC, program counter): o endereço da próxima instrução a executar.
  • Apontador de pilha (SP, stack pointer): o endereço do topo da pilha de execução.
  • Registrador de status (PSW, program status word): bits sobre a situação da CPU. A última comparação deu zero? Deu negativo? Houve estouro? A CPU está em modo usuário ou kernel? Interrupções estão ligadas?
  • Enquanto o processo executa, esses valores moram nos registradores físicos. Quando ele sai da CPU, o SO copia todos para a memória do kernel: é a troca de contexto.

O processo A está no meio de um loop, com o contador i valendo 731, quando o temporizador interrompe e o SO passa a CPU para B. Para A continuar depois sem perceber nada, o SO precisa ter guardado:

  • em que instrução A parou: o PC;
  • os valores que estavam nos registradores, inclusive i = 731, se o compilador deixou i num registrador;
  • a memória de A intacta, sem nada escrito por B (espaço de endereçamento);
  • os arquivos que A tinha abertos e em que posição de cada um ele estava lendo (contexto de software).

Contexto de software

As características e os limites do processo, mantidos pelo SO. O livro separa em três grupos: identificação, quotas e privilégios.

  • Identificação: o PID (process identifier, um número único para cada processo vivo, como 4182), o dono (o usuário que criou o processo, identificado pelo UID, que define o que ele pode acessar), o PID do processo pai e o nome do programa.
  • Quotas: limites de recursos. Máximo de arquivos abertos, de memória, de subprocessos e threads, tamanho do buffer de E/S, tempo de CPU.
  • Privilégios: o que o processo pode fazer além do comum, como mudar a prioridade de outros processos, desligar o sistema ou ler arquivos de outros usuários. O administrador (root no Linux) tem todos.
  • Entram aqui também a prioridade de execução e a lista de arquivos abertos.
  • No Linux, ulimit -n mostra o limite de arquivos abertos (1024 é um valor comum).

Espaço de endereçamento

A faixa de endereços de memória que o processo pode usar, e o que há dentro dela. Cada processo tem o seu, isolado dos outros.

  • O isolamento vem da memória virtual (aula 02): o endereço 0x4000 de A e o 0x4000 de B levam a lugares físicos diferentes.
  • Quatro regiões, de baixo para cima: código, dados globais, heap e pilha de execução.
  • Código (também chamado texto): as instruções do programa. Só leitura, para um bug não reescrever o próprio programa.
  • Dados globais: as variáveis globais e estáticas, que existem do começo ao fim da execução.
  • Heap: memória pedida durante a execução, quando o tamanho só é conhecido na hora: malloc em C, new em Java, todo objeto em Python. Cresce para cima.
  • Pilha de execução: os blocos das chamadas de função. Cresce para baixo, a partir do topo do espaço.

Onde mora cada coisa num programa em C:

int total = 0;                       // dados globais
int soma(int n) {                    // as instruções de soma ficam no código
    int i, s = 0;                    // i e s: pilha de execução
    int *v = malloc(n * sizeof(int)); // v: pilha de execução; o vetor: heap
    for (i = 0; i < n; i++) s += v[i];
    free(v);
    return s;
}

Pilha de execução

A pilha de execução (stack) guarda um bloco para cada chamada de função em andamento, com as variáveis locais, os parâmetros e o endereço para onde voltar. Cada chamada empilha um bloco; cada return tira o bloco do topo.

  • Segue a regra da pilha como estrutura de dados (aula 01): o último bloco que entra é o primeiro que sai.
  • O SP guarda o endereço do topo.
  • Entre o heap e a pilha de execução sobra um espaço livre. Uma recursão sem fim gasta esse espaço até o fim e causa o famoso stack overflow: o SO encerra o processo.
  • main chama soma, que chama malloc: a primeira a terminar é malloc, e o bloco dela é o que está no topo.

PCB: a ficha do processo no kernel

O bloco de controle do processo (PCB, process control block) é a estrutura de dados do kernel, uma por processo, que guarda o contexto de hardware, o contexto de software, as informações sobre o espaço de endereçamento e o estado do processo.

  • Funciona como um prontuário médico: quem é o processo, em que situação está e tudo o que é preciso para retomá-lo de onde parou.
  • O PCB fica na memória do kernel, fora do alcance do processo. Assim ele não consegue, por exemplo, aumentar a sua prioridade.
  • Tabela de processos: a coleção de todos os PCBs do sistema. No Linux, cada PCB é uma struct task_struct. Os comandos ps e top e o Gerenciador de Tarefas do Windows mostram o que está nela.
  • No Linux dá para espiar parte do PCB de um processo em /proc/<PID>/status.

PCB = contexto de hardware (registradores, PC, SP, status) + contexto de software (PID, dono, prioridade, quotas, privilégios, arquivos abertos) + informações do espaço de endereçamento (código, dados, heap, pilha de execução) + estado.

Estados do processo e filas

Ao longo da vida, um processo passa por cinco estados: novo, pronto, executando, espera e terminado. O SO anota o estado atual no PCB e decide o que fazer com cada processo olhando para ele.

  • Como um paciente no pronto-socorro: chegando (fazendo a ficha), na sala de espera, sendo atendido, esperando um exame ficar pronto, ou de alta.
  • Novo (criação): o SO está montando o PCB e reservando memória. O processo ainda não disputa a CPU.
  • Pronto: tem tudo para executar e só falta a CPU. Espera na fila de prontos.
  • Executando: está usando a CPU agora. Com um core, só um processo por vez fica neste estado; com 4 cores, até 4.
  • Espera (bloqueado): aguarda um evento de fora: uma E/S terminar, um tempo passar, um recurso ser liberado. Dar a CPU a ele não adianta nada.
  • Terminado: acabou; o SO libera tudo (como um processo termina).
  • Quem move o processo entre pronto e executando é o scheduler.
  • A fila de prontos é, na prática, uma lista ligada de PCBs. Os processos em espera ficam em outras filas, uma para cada dispositivo ou evento (fila do disco, fila do teclado).
  • Machado & Maia citam um caso a mais: quando falta memória, o SO pode tirar um processo pronto ou em espera da memória e guardá-lo no disco. Ele continua pronto ou em espera, só que fora da memória, e precisa voltar para ela antes de executar. Essa técnica é o swapping, da aula 06.

Transições válidas: novo → pronto, pronto → executando, executando → espera, espera → pronto, executando → pronto (preempção) e executando → terminado. Não existem espera → executando nem pronto → espera.

  • Espera → executando não existe. Quem sai da espera vai para a fila de prontos e disputa a CPU de novo.
  • Pronto → espera não existe. Só quem está executando consegue pedir E/S, porque pedir é executar uma syscall.
  • Executando → pronto é involuntário (preempção). Executando → espera é voluntário (o processo pediu algo).

A tarefa que lê o sensor passa a maior parte do tempo em espera, aguardando a próxima amostra. Exemplo fora do cenário: uma tarefa que acorda a cada 50 ms e calcula por 3 ms fica 47 ms em espera, entra na fila de prontos quando o temporizador a acorda e só calcula quando chega a vez dela. Scheduler, dispatcher e preempção

O scheduler (escalonador) é a rotina do kernel que escolhe qual processo pronto vai para a CPU. O dispatcher (despachante) executa a escolha: carrega o contexto do processo escolhido e salta para o PC dele.

  • Os critérios de escolha (ordem de chegada, prioridade, revezamento) são o assunto da aula 06.
  • Preempção: tirar a CPU de um processo que ainda queria continuar, porque o quantum acabou ou porque chegou um processo mais prioritário. Um SO preemptivo usa o temporizador para isso.
  • Sem preempção, um programa preso num loop infinito trava a máquina inteira. Acontecia no Windows 3.1, que dependia de cada programa ceder a CPU por conta dele.

Troca de contexto

A troca de contexto (context switch) é a passagem da CPU de um processo para outro. Acontece sempre que um processo sai da CPU: por preempção (o temporizador interrompeu), porque ele pediu E/S, ou porque terminou.

  • O tempo gasto na troca não é trabalho útil de ninguém: é overhead.

De A para B:

  • Salva o contexto de hardware de A no PCB de A.
  • Atualiza o estado de A no PCB (executando → pronto, se foi preempção) e põe A na fila.
  • O scheduler escolhe o próximo, B.
  • O dispatcher carrega nos registradores o contexto guardado no PCB de B.
  • Troca o mapa de memória para o espaço de endereçamento de B (a tabela de páginas).
  • Volta ao modo usuário e salta para o PC de B, que continua exatamente de onde tinha parado.

Quanto custa a troca de contexto: overhead e quantum

Overhead é o tempo e os recursos gastos com gerenciamento, que não são trabalho útil de nenhum processo. Durante a troca de contexto, a CPU só executa código do kernel: nenhum processo avança.

  • Custo direto: salvar e carregar registradores, rodar o scheduler, trocar o mapa de memória. Em máquinas atuais fica na faixa de 1 a 10 µs.
  • Custo indireto: a cache e a TLB (aula 02) estão cheias de dados do processo antigo. Os primeiros acessos do novo processo dão miss, e isso pode custar mais do que a troca em si.
fração útil = q / (q + s) overhead = s / (q + s)
espera até voltar a executar (pior caso) = (n − 1) × (q + s)
  • q: o quantum, o tempo que cada processo usa antes de ser trocado. s: o tempo de uma troca. A cada ciclo, a CPU trabalha q e perde s.
  • n: processos revezando. Cada um espera os outros n − 1 terminarem a vez deles.
  • q = 4 ms e s = 20 µs = 0,02 ms. Fração útil = 4 / (4 + 0,02) = 4 / 4,02 ≈ 0,995. A CPU trabalha 99,5 % do tempo; o overhead é 0,5 %.
  • Mesma troca com q = 0,1 ms: 0,1 / (0,1 + 0,02) = 0,1 / 0,12 ≈ 0,833. Agora 16,7 % do tempo vai embora em trocas.
  • 5 processos, q = 4 ms e s = 0,02 ms: 4 × 4,02 = 16,08 ms até voltar a executar.
  • Quantum curto: resposta rápida, overhead alto. Quantum longo: overhead baixo, resposta lenta. Mexa nos números na figura abaixo.

A troca de contexto é overhead: enquanto ela acontece, nenhum processo avança. Fração útil = q / (q + s). Quantum menor dá resposta mais rápida e mais overhead.

Exemplo fora do cenário: um monitor cardíaco precisa tratar cada batida em até 20 ms e divide a CPU com outras 3 tarefas, com q = 4 ms e s = 15 µs. No pior caso, a tarefa dele espera (n − 1) × (q + s) = 3 × 4,015 = 12,045 ms antes de começar, e sobram menos de 8 ms para o cálculo. Como um processo nasce: subprocesso, fork e exec

Processo criado por outro é um subprocesso (processo filho) do processo pai. Machado & Maia citam três origens:

  • Logon interativo: ao entrar no sistema com usuário e senha, o SO cria um processo para atender aquele usuário.
  • Shell, o interpretador de comandos: cada comando digitado (ls, python app.py) vira um processo novo.
  • Por outro processo: fork no Unix e no Linux, CreateProcess no Windows.
  • Pais e filhos formam uma árvore de processos (veja com pstree no Linux). O filho herda parte do contexto do pai, como o dono e os arquivos abertos.
  • Processo independente: criado sem vínculo com quem o criou. Se o criador termina, ele continua.
  • fork: no Unix, cria uma cópia quase idêntica do processo que chamou. Mesmo código, cópia da memória, PID novo. A chamada "retorna duas vezes": no filho devolve 0, no pai devolve o PID do filho.
  • exec: troca o programa que o processo está executando por outro, mantendo o mesmo PID. O shell roda cada comando com fork seguido de exec no filho.
  • O lado ruim de dividir uma aplicação em subprocessos: cada criação aloca PCB e espaço de endereçamento novos, o que custa tempo; e como as memórias são separadas, conversar entre processos exige mecanismos do SO (arquivos, pipes, mensagens), que são lentos. Esse problema é o ponto de partida das threads.
import os                         # só funciona em Linux e macOS
pid = os.fork()                   # daqui em diante existem dois processos
if pid == 0:
    print("sou o filho, PID", os.getpid())
    os.execvp("ls", ["ls", "-l"]) # o filho passa a ser o programa ls
else:
    print("sou o pai; meu filho tem PID", pid)
    os.wait()                     # o pai fica em espera até o filho terminar

Como um processo termina

Um processo termina por fim normal, por erro ou porque foi morto. O SO fecha os arquivos, libera a memória e apaga o PCB.

  • Fim normal: o programa chama exit (o return do main faz isso).
  • Erro: uma exceção que o programa não trata, como divisão por zero ou acesso a endereço inválido.
  • Morto por outro processo com permissão para isso (kill no Linux, "Finalizar tarefa" no Windows), pelo fim da sessão do usuário ou por estourar uma quota.
  • Processo zumbi: no Unix, o PCB fica até o pai ler o código de saída do filho; enquanto isso, o filho é um zumbi.

Sinais

Sinal é um aviso que o SO entrega a um processo de forma assíncrona, como uma interrupção, só que para processos. Cada sinal tem um número e um nome.

  • O processo pode registrar uma função do próprio programa para tratar a maioria dos sinais. Se não registrar, vale a ação padrão, em geral terminar.
  • Ctrl+C envia SIGINT.
  • kill -9 envia SIGKILL, que não pode ser ignorado.
  • Acessar memória proibida gera SIGSEGV (o segmentation fault).

Tipos de processo: foreground, background e processos do sistema

Foreground (primeiro plano): processo ligado ao console do usuário, que lê do teclado e escreve na tela enquanto roda. Background (segundo plano): roda sem conversar direto com o usuário.

  • No Linux, comando & manda para o segundo plano.
  • A saída de um processo pode ser a entrada de outro: ls | sort liga dois processos por um pipe.
  • Processo do sistema (daemon no Unix, serviço no Windows): processo que implementa uma função do próprio SO e fica em background. Exemplos: agendador de tarefas (cron), fila de impressão, serviços de rede, auditoria e contabilização de uso.

CPU-bound e I/O-bound

CPU-bound (limitado pela CPU): passa a maior parte do tempo calculando e ficaria mais rápido com uma CPU mais rápida. I/O-bound (limitado por E/S): passa a maior parte do tempo em espera por E/S e ficaria mais rápido com E/S mais rápida.

  • CPU-bound: compactar um vídeo, treinar um modelo de aprendizado de máquina, simulação numérica.
  • I/O-bound: editor de texto esperando teclas, servidor web esperando a rede, banco de dados esperando o disco.
  • O mesmo processo pode mudar de perfil ao longo da execução.
  • Schedulers costumam favorecer os I/O-bound: eles usam a CPU por pouco tempo, pedem E/S e liberam a CPU logo (aula 06).

Exemplo fora do cenário: num termostato, ler a temperatura uma vez por segundo e mandar por Wi-Fi é trabalho I/O-bound; aplicar um filtro de 500 coeficientes a cada leitura puxa para CPU-bound. Threads: monothread e multithread

Uma thread (em inglês, "fio") é um fluxo de instruções dentro de um processo e a menor unidade que o SO escalona. Cada thread tem contexto de hardware, pilha de execução e estado só seus, e compartilha com as outras threads do processo o espaço de endereçamento e o contexto de software.

  • Se o processo é uma casa com móveis e despensa, as threads são as pessoas que moram nela: cada uma faz uma coisa diferente, e todas usam a mesma cozinha.
  • Monothread: cada processo tem um único fluxo de execução, ou seja, um só PC. Para fazer duas coisas ao mesmo tempo, a aplicação precisa de dois processos. Era assim no MS-DOS e nos primeiros Unix.
  • Multithread: um processo pode ter vários fluxos de execução, todos dentro do mesmo espaço de endereçamento.
  • Com threads, o processo vira a unidade de alocação de recursos.
  • TCB (thread control block): onde o kernel guarda a parte individual de cada thread. É um bloco menor que o PCB, ligado a ele.

Três fluxos no mesmo processo, em Python:

import threading, time

contador = 0                         # global: as três threads enxergam o mesmo

def tarefa(nome, n):
    feitos = 0                       # local: na pilha de execução desta thread
    for _ in range(n):
        feitos += 1
        time.sleep(0.01)             # esta thread vai para espera; as outras seguem
    print(nome, "terminou:", feitos)

ts = [threading.Thread(target=tarefa, args=(f"T{i}", 5)) for i in range(3)]
for t in ts: t.start()               # três fluxos rodando no mesmo processo
for t in ts: t.join()                # a thread principal espera as três

Threads do mesmo processo compartilham o espaço de endereçamento (código, dados globais, heap) e os arquivos abertos. Cada thread tem PC, registradores, pilha de execução e estado só seus.

Por que usar threads, e o preço de compartilhar

Threads saem mais baratas que subprocessos para criar, trocar e conversar. O preço: nada protege uma thread da outra dentro do mesmo processo.

  • O problema de partida: um servidor web atende mil clientes ao mesmo tempo. Com um subprocesso por cliente, são mil PCBs, mil espaços de endereçamento e, para compartilhar a mesma cache de páginas, mil processos conversando por mecanismos lentos do SO.
  • Criar e trocar é mais barato: não há espaço de endereçamento novo para montar. Trocar entre threads do mesmo processo não troca o mapa de memória, e a cache e a TLB continuam úteis. Criar uma thread costuma ser uma ordem de grandeza mais rápido que criar um processo.
  • Comunicação direta: as threads leem e escrevem as mesmas variáveis globais e o mesmo heap, sem pedir nada ao SO.
  • O programa continua respondendo enquanto uma thread espera E/S. Exemplo clássico: num editor de texto, uma thread trata o teclado, outra confere a ortografia e outra salva o arquivo de tempos em tempos.
  • Aplicações cliente-servidor: uma thread por requisição, todas consultando a mesma cache em memória.
  • Com vários cores, threads do mesmo processo executam de fato ao mesmo tempo, cada uma num core (paralelismo).
  • Preço: não há proteção entre threads do mesmo processo. Uma pode estragar os dados da outra, por bug ou por azar na ordem de execução.
  • Preço: um erro fatal numa thread (acesso a endereço inválido, por exemplo) derruba o processo inteiro, com todas as threads.
  • Duas threads somando 1 no mesmo contador podem perder incrementos: quando duas threads mexem no mesmo dado, a ordem de execução muda o resultado. Esse problema, e como evitá-lo, é a aula 05.

Exemplo fora do cenário: num leitor de código de barras, uma thread lê o scanner e outra grava no banco de dados. Se o banco demora 200 ms, só a thread do banco fica em espera e a leitura continua. Concorrência e paralelismo

Concorrência: várias tarefas em andamento no mesmo intervalo de tempo, revezando a CPU; num instante qualquer, só uma executa. Paralelismo: várias tarefas executando no mesmo instante, em cores diferentes.

  • Na concorrência, a alternância rápida dá a impressão de simultaneidade.
  • Paralelismo exige mais de um core.
  • Todo programa paralelo é concorrente, mas um programa concorrente num único core não tem paralelismo nenhum.

Threads de usuário (ULT)

ULT (user-level thread, a TMU do livro): thread criada e escalonada por uma biblioteca de threads que roda dentro do processo, em modo usuário. O kernel nem sabe que ela existe: para ele, o processo é monothread.

  • Quem cria as threads e decide qual delas roda? Uma biblioteca dentro do próprio processo (ULT) ou o kernel (KLT). O livro ainda descreve uma mistura das duas.
  • Vantagem: criar e trocar de thread é só uma chamada de função na biblioteca, sem syscall e sem mudar de modo. Leva nanossegundos.
  • Vantagem: funciona até num SO que não conhece threads, e a aplicação pode escalonar as threads do jeito que preferir.
  • Chamada bloqueante: aquela que deixa quem chamou em espera até o serviço terminar, como read do disco.
  • Problema: uma chamada bloqueante bloqueia o processo inteiro. O kernel põe "o processo" em espera, e todas as threads param junto.
  • Problema: não há paralelismo. O kernel só vê uma entidade para escalonar, então ela usa um core por vez.
  • Problema: o temporizador interrompe o processo, não a thread. Se uma thread não cede a vez, a biblioteca não consegue tirá-la.
  • Bibliotecas tentam contornar trocando chamadas bloqueantes por versões não bloqueantes.

Threads de kernel (KLT)

KLT (kernel-level thread, a TMK do livro): o kernel cria, conhece e escalona cada thread, por syscalls. Cada uma tem estado no kernel.

  • Vantagem: uma thread bloqueada em E/S não trava as outras; o kernel escalona outra thread do mesmo processo.
  • Vantagem: paralelismo real. Num processador com 4 cores, 4 threads do mesmo processo rodam ao mesmo tempo.
  • Problema: criar, trocar e sincronizar exigem entrar no kernel, o que é bem mais lento que uma chamada de função. E o kernel guarda uma estrutura para cada thread, o que limita quantas cabem.

Os três mapeamentos: N:1, 1:1 e M:N

Os modelos de mapeamento dizem quantas threads de usuário ficam penduradas em cada thread do kernel.

  • N:1 (muitos para um): várias ULT sobre uma única entidade do kernel. É o modelo de ULT puro. Exemplos: as green threads das primeiras versões do Java, a biblioteca GNU Portable Threads.
  • 1:1 (um para um): cada thread que o programa cria é uma KLT. É o modelo do Linux (pthreads, com a biblioteca NPTL), do Windows e do Java atual.
  • M:N (muitos para muitos, o modo híbrido do livro): M threads de usuário distribuídas sobre N threads do kernel, com N ≤ M. Junta troca rápida, paralelismo e tolerância a bloqueio. O preço é a complexidade: dois schedulers, um na biblioteca e outro no kernel, que precisam se entender. Exemplos: o Solaris antigo, as goroutines do Go, as threads virtuais do Java 21.
  • Scheduler activations: o mecanismo que o livro descreve para fazer o híbrido funcionar. Quando uma thread vai bloquear, o kernel avisa a biblioteca (uma chamada "de baixo para cima", a upcall), e a biblioteca coloca outra thread de usuário para rodar.
  • Na figura abaixo, os três modelos com o mesmo programa: quatro threads, dois cores e uma chamada bloqueante.

ULT: troca rápida, mas uma chamada bloqueante bloqueia o processo todo e não há paralelismo. KLT: o kernel escalona cada thread, há paralelismo real e uma thread bloqueada não trava as outras, ao custo de mais overhead.

Exemplo fora do cenário: num drone com biblioteca N:1, se a thread de telemetria faz um envio de rádio bloqueante de 30 ms, a thread que controla os motores para junto por 30 ms. Pergunta: o que acontece com a leitura do sensor quando o envio por BLE bloqueia, conforme o modelo de threads escolhido?

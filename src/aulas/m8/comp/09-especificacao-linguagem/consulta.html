Resumo

Decidir para que serve vem antes de escrever a gramática.

Uma linguagem nova começa por uma pergunta: para que e para quem ela serve. Esta aula mostra o que é uma linguagem específica de domínio, as diretrizes para projetar uma e como juntar léxico, gramática e regras de significado numa especificação.

  • DSL é linguagem de uma área só (SQL, HTML, fórmula do Excel). Linguagem de propósito geral serve para qualquer programa (Java, Python).
  • Com uma DSL você escreve um modelo do problema, e um gerador o transforma em código. Trocar o gerador reaproveita o modelo.
  • Ganha: notação de quem conhece o domínio, abstração e produtividade. Paga: custo para criar, gente que entenda de linguagem e do domínio, usuários aprendendo.
  • Karsai et al. listam 26 diretrizes em cinco grupos: propósito, realização, conteúdo, sintaxe concreta e sintaxe abstrata. Elas brigam entre si, e o projeto decide o peso de cada uma.
  • Sintaxe concreta é o texto; abstrata é a árvore que sobra sem a pontuação. O que é diferente no texto tem de ser diferente na árvore, e o layout não deve mudar o significado.
  • A especificação traz os tokens (expressões regulares), a gramática (BNF ou EBNF), as regras que a gramática não confere e exemplos válidos e inválidos.
  • HTML não é linguagem de programação e mesmo assim é DSL: o "L" é de linguagem.
  • Açúcar sintático não deixa a linguagem dizer nada novo; só muda o jeito de escrever.
  • Começar do zero é a última opção. Antes, tente compor ou reaproveitar uma linguagem pronta.
  • Usar = para atribuição e para igualdade na mesma linguagem é o exemplo clássico do que evitar.

Linguagem específica de domínio × propósito geral

Uma DSL diz pouco fora da sua área, e muito dentro dela.

Uma linguagem específica de domínio (DSL, domain specific language) tem notação e abstrações feitas para uma área só. Uma linguagem de propósito geral (GPL), como Java ou Python, serve para escrever qualquer programa.

  • O domínio é a área de conhecimento da linguagem, com conceitos, regras e termos próprios: medicina, tributos, direito, ensino a distância.
  • Uma DSL é menos complexa que uma GPL. Ela é feita junto com especialistas da área e costuma ser usada por eles, que não programam, mas dominam o assunto.
  • O autor de referência no assunto, segundo o vídeo, é Martin Fowler.
  • Pode ser textual (SQL) ou gráfica. As placas de trânsito são uma DSL gráfica: poucos símbolos, sentido preciso, só servem no trânsito.
  • Para Karsai et al., DSLs são criadas para aumentar a produtividade num domínio, mas muitas servem só para um problema bem estreito e não têm qualidade para muita gente usar.

  • "HTML nem é linguagem de programação, então não é DSL." Errado: a definição fala em linguagem de programação ou de especificação.
  • DSL não precisa ser executável. Placas de trânsito e diagramas só de documentação também contam.

Modelo, metamodelo e gerador de código

O exemplo do vídeo: um menu de wiki.

Com uma DSL você escreve um modelo do problema. Um gerador de código lê o modelo e produz o resto: código, dados, configuração. O metamodelo é o modelo dos modelos: diz que elementos um modelo pode ter.

  • O caminho: do campo das ideias para um modelo perto do domínio; de lá, um mapeamento gera código, e o código vira código de máquina.
  • O gerador primeiro faz o parse do modelo, isto é, lê e entende a estrutura, como um compilador. Depois gera os artefatos: código, dados, arquivos de configuração, diagramas.
  • Você escreve a linguagem uma vez e cria quantos geradores quiser. Vários produtos saem da mesma ideia.
  • Três palavras do vídeo: modelo representa o problema; plataforma é o ambiente onde ele é resolvido; integração junta modelos em uma ou mais plataformas.
  • O metamodelo está para o modelo como a gramática está para o programa.
  • Exemplo do vídeo, de um artigo do autor de 2010: uma DSL para montar o menu de uma wiki acessível.
  • Metamodelo: a wiki tem zero ou mais menus hierárquicos. Cada menu tem título, tipo (vertical ou horizontal) e a profundidade máxima mostrada. Cada item tem uma ação (para onde navega) e um rótulo (o texto), e pode ter subitens.
  • Modelo: o metamodelo preenchido. "Créditos", "Sobre nós" e, dentro de "Sobre nós", "Estatutos" com 2010 e 2009.
  • Gerador: lê o modelo e escreve o menu web acessível, que funciona pelo teclado e com leitor de tela, não só com o mouse.
  • Depois de 2010 vieram Bootstrap e outras tecnologias. Basta trocar o gerador: a leitura do modelo e o próprio modelo continuam iguais, e quem cria os sites (jornalistas, criadores de conteúdo) não precisa de treino novo.
  • Confundir modelo e metamodelo. O metamodelo é a regra (quais elementos existem); o modelo é o que a pessoa escreve seguindo a regra.

Vantagens, custos e ferramentas

O prato dos custos pesa mais no começo.

Uma DSL troca um custo alto de criação por ganho de quem a usa no dia a dia. Ferramentas próprias (language workbenches) baixam parte desse custo.

As 26 diretrizes em cinco grupos

Os grupos seguem as etapas do projeto.

Karsai et al. reúnem 26 diretrizes para projetar uma DSL, tiradas da literatura e da experiência deles. Elas estão agrupadas pela etapa do projeto, para você olhar só as que importam naquele momento.

  • A discussão é antiga. Em 1973, Hoare pedia simplicidade, segurança, tradução rápida, código objeto eficiente e legibilidade. Em 1974, Wirth discutiu o projeto de linguagens e de compiladores.
  • De lá para cá, os computadores ficaram rápidos, então velocidade e espaço pesam menos, e geradores de analisadores fazem o parser por você.
  • Paige et al. propõem simplicidade, unicidade, consistência e escalabilidade para linguagens de modelagem, mas não dizem como chegar lá. Muitas diretrizes não viram uma conta que uma ferramenta confira.
  • O foco do artigo são DSLs textuais, mas as diretrizes valem também para as gráficas.
  • A semântica não é um grupo: ela pesa em todas as etapas.
  • As diretrizes às vezes se contradizem, e o peso de cada uma muda com o projeto. Para uma linguagem de configuração usada num projeto só, entregar logo vale mais que caprichar na usabilidade.
  • Os autores dizem que a lista não está completa e muda com o tempo: algumas regras dos anos 1970 já importam menos.

Propósito (1–3): para que e para quem

Os usos decidem os conceitos.

A linguagem depende tanto do que ela descreve quanto do que se faz com ela. Por isso a primeira atividade é analisar o objetivo: os usos, as pessoas e a coerência de cada recurso com esse objetivo.

  • Diretriz 1, identifique os usos cedo. Os mais comuns são documentar conhecimento e gerar código. Há outros: definir ou gerar testes, verificação formal, análises automáticas, configurar o sistema na implantação ou na execução e, cada vez mais, simulação.
  • O uso decide o que a linguagem pode oferecer. Com conceitos subespecificados, como Statecharts não determinísticos, nem sempre dá para gerar código: o gerador precisa de uma escolha concreta.
  • Se o alvo é uma máquina pequena (celular, central de um carro), os conceitos de alto nível precisam ser pensados para gerar código otimizado. Para simular ou validar requisitos, a eficiência pesa pouco.
  • Diretriz 2, faça perguntas. Encaixe os usos no processo de desenvolvimento: quem vai modelar na DSL? Quem revisa os modelos, e quando? Quem usa os modelos, e para quê?
  • Com as respostas, reveja se a linguagem está complexa demais ou se falta algum elemento do domínio, e prepare tutoriais para cada usuário.
  • Diretriz 3, seja consistente. Cada recurso tem de contribuir para o propósito; se não contribui, sai. Numa linguagem independente de plataforma, todos os recursos precisam ser independentes de plataforma.
  • No menu da wiki (vídeo): o uso é gerar código de menu; quem modela são jornalistas e criadores de conteúdo; o modelo é revisado quando o site muda. Daí a linguagem ter só menus, itens, ações e rótulos.
  • Começar pela sintaxe. Sem saber o uso, você não sabe se pode deixar algo em aberto (documentação) ou se tudo precisa virar código (geração).

Realização (4–7): texto ou desenho, do zero ou reaproveitando

Pese as duas formas contra o que os usuários preferem.

Na realização você decide como construir a linguagem: textual ou gráfica, e se ela nasce do zero ou reaproveita linguagens, gramáticas e sistemas de tipos que já existem. A ordem de preferência é reaproveitar; do zero, só quando nada serve.

  • Diretriz 4, escolha com cuidado entre gráfica e textual. Textual costuma ser mais rápida de desenvolver e não depende de plataforma nem de ferramenta. Gráfica dá melhor visão geral e facilita entender o modelo. Pese isso contra o que os usuários preferem; depois escolha a ferramenta.
  • Diretriz 5, componha linguagens que já existem. A forma mais útil é embutir uma linguagem sem mudar nada nela: a OCL entra em outras linguagens para escrever restrições. Uma variante é a linguagem hospedeira ter "buracos" previstos para outras.
  • Os conceitos compostos precisam combinar. Na UML, diagramas de classes e Statecharts combinam porque os dois são orientados a objetos. E evite construções parecidas com significados diferentes.
  • Diretriz 6, reaproveite definições de linguagem. Se não dá para compor, parta da definição de outra linguagem (estender ou especializar), em vez de começar do zero. A sintaxe concreta e a abstrata ganham, e o usuário reconhece notações familiares.
  • Há "padrões de linguagem", como padrões de projeto: expressões, expressões primárias e comandos têm quase a mesma forma em todas as linguagens. Os sites de geradores de parser, como o do ANTLR, têm gramáticas prontas para começar.
  • Diretriz 7, reaproveite um sistema de tipos. Projetar um é das tarefas mais difíceis, por causa de espaços de nomes, tipos genéricos, conversões e polimorfismo. Um sistema de tipos estranho também afasta o usuário. Adapte um conhecido, como o da OCL ou o do Java.
  • Uma DSL de consultas para um sistema de notas pode embutir SQL sem mudanças (diretriz 5), em vez de inventar outra sintaxe de busca.
  • Juntar duas linguagens em que o mesmo símbolo quer dizer coisas diferentes. A composição só funciona se os conceitos se encaixam.

Conteúdo (8–13): só o necessário, sem repetir conceito

Um funil: o domínio inteiro não cabe na linguagem.

O conteúdo são os elementos da linguagem. Entram só os conceitos do domínio que servem aos usos, no menor número possível, sem dois conceitos para a mesma coisa e sem elementos que obriguem a gerar código lento.

  • Diretriz 8, reflita só os conceitos necessários. Escreva cedo alguns modelos de exemplo: eles mostram como o domínio aparece na linguagem e servem para os especialistas darem opinião.
  • Diretriz 9, mantenha simples. Uma linguagem nova já exige ferramentas e processos novos; se ela é complexa, é mais difícil de adotar e entrega menos do que prometia. As diretrizes 10 a 12 dizem como.
  • Diretriz 10, evite generalidade desnecessária. "Vamos generalizar para mudanças futuras" complica e atrasa a adoção. Projete só o necessário.
  • Diretriz 11, limite o número de elementos. Para domínios grandes, divida em sublinguagens: a UML tem diagramas de estrutura, de comportamento e de implantação, cada um com poucos conceitos.
  • Outra saída são bibliotecas: elementos saem da linguagem e viram modelos reaproveitáveis. Entrada e saída é parte da linguagem Pascal e fica na biblioteca em C++. Para isso, a linguagem precisa de algum jeito de definir e importar coisas.
  • Diretriz 12, evite redundância conceitual. Dois conceitos para o mesmo fato fazem cada pessoa escrever de um jeito. Em C++, class e struct só diferem no acesso padrão aos membros (privado e público), e guias de codificação acabam proibindo um deles.
  • Diretriz 13, evite elementos ineficientes. O usuário mexe no modelo, mas o código gerado decide a eficiência do sistema. A eficiência deve depender do modelo, não de um elemento caro escondido na linguagem.
  • Java não tem operador que devolva todas as instâncias de uma classe: ele gastaria memória e tempo em qualquer programa. Quem precisa, implementa; assim só o usuário pode introduzir a ineficiência.
  • Generalizar "para o futuro" parece prudente e é o que a diretriz 10 desaconselha.

Sintaxe concreta e sintaxe abstrata

A pontuação some; a estrutura fica.

A sintaxe concreta é a forma que você lê e escreve: texto (ou desenho) com palavras-chave, pontuação e espaços. A sintaxe abstrata é a estrutura interna que a ferramenta guarda: quais elementos existem e quem está dentro de quem, sem o que só servia para ler.

  • No artigo: a concreta é a representação legível, externa; a abstrata é a representação interna. O artigo trata primeiro da concreta e depois da abstrata.
  • Linguagens diferentes podem ter a mesma sintaxe abstrata. x = a + 2;, x := a + 2 e (setq x (+ a 2)) viram a mesma árvore: atribuição de uma soma.
  • A sintaxe abstrata costuma ser uma árvore, a árvore sintática abstrata (AST). Geradores e transformações trabalham sobre ela; pretty printing faz o caminho de volta, da árvore para um texto bem formatado.
  • A árvore de derivação é outra árvore: ela tem um nó para cada variável usada (EXPR, SOMA, TERMO…) e para cada terminal, inclusive ;. A abstrata guarda só o que tem significado.
  • A Figura 1 lê a mesma ordem em três sintaxes concretas e monta uma árvore só. O último passo mostra o que acontece quando um símbolo quer dizer duas coisas.
  • Chamar a árvore de derivação de sintaxe abstrata. Na derivação de b = (y - 2) * z; da aula 08 aparecem FATOR, TERMO, os parênteses e o ponto e vírgula; na abstrata, só atribuição, multiplicação e subtração.

Sintaxe concreta (14–17): notação que já se conhece

Reaproveite o sentido que os símbolos já têm.

A sintaxe concreta precisa ser fácil de ler. A regra geral: copie a notação que os especialistas já usam, mantenha o sentido de sempre dos símbolos, deixe cada elemento fácil de reconhecer e use açúcar sintático com moderação.

  • Diretriz 14, adote a notação que os especialistas já usam. Eles usam a mesma linguagem por anos e não querem aprender outra. Consultas a banco de dados se escrevem em SQL, mesmo que só uma parte da DSL faça consultas: SQL pode ir embutida.
  • Se não existe notação no domínio, chegue o mais perto possível de outras notações da área ou de linguagens comuns. Expressões aritméticas são o exemplo de notação que todo mundo aceita.
  • Diretriz 15, use notação descritiva. Reaproveite termos e símbolos conhecidos, com o mesmo sentido: + é soma ou algo parecido; vírgula e ponto e vírgula separam. No LaTeX, a letra grega α se escreve \alpha, pelo nome.
  • Palavras-chave com sentido conhecido, fáceis de identificar, poucas e fáceis de lembrar. Um editor que destaca palavras-chave ajuda.
  • Diretriz 16, deixe os elementos distinguíveis. Numa DSL gráfica, cor sozinha falha quando o modelo é impresso em preto e branco. Numa textual, as palavras-chave separam os tipos de elemento e precisam estar em posições que não obriguem o leitor a voltar atrás.
  • Tirar palavras-chave para escrever menos é um motivo fraco: o modelo é lido muito mais vezes do que escrito, então projete pensando em quem lê.
  • Diretriz 17, use açúcar sintático com cuidado. Açúcar não aumenta o que a linguagem expressa; melhora a leitura e às vezes ajuda o parser. "Se não dá para fazer um parser eficiente, a linguagem provavelmente é difícil também para gente."
  • Açúcar demais distrai, e várias formas para o mesmo conceito atrapalham a conversa entre pessoas que preferem formas diferentes.
  • O for aprimorado do Java 5 é açúcar: for (int x : v) soma += x; faz o mesmo que for (int i = 0; i < v.length; i++) soma += v[i];. Ele contraria a diretriz 12 (dois jeitos de repetir), mas percorrer um vetor é tão comum que a forma curta compensa.
  • Açúcar sintático deixa a linguagem mais expressiva? Não: tudo o que ele escreve já dava para escrever.
  • Trocar o sentido de um símbolo conhecido (um + que não soma) quebra a diretriz 15, mesmo que a gramática esteja certa.

Sintaxe concreta (18–22): comentários, arquivos e estilo

Comentário, import e nome qualificado.

O resto da sintaxe concreta trata de como o modelo é escrito no dia a dia: comentários, divisão em arquivos, equilíbrio entre curto e claro, um estilo só e regras de estilo que ficam fora da gramática.

  • Diretriz 18, permita comentários. Eles explicam decisões para outras pessoas e permitem trabalhar em grupo. Use as formas conhecidas, /* … */ e // …; numa DSL gráfica, caixas de texto e dicas.
  • Comentários com estrutura geram documentação, como o Javadoc gera páginas HTML. Hoare dizia que o propósito de uma linguagem é ajudar a documentar programas. A linguagem pode até definir o formato do comentário.
  • Diretriz 19, dê estrutura de organização. Sistemas grandes ficam em muitos arquivos; pacotes e diretórios, como no Java, evitam uma pasta lotada.
  • Arquivos precisam se referir uns aos outros: import deixa visível o que outro arquivo define, e nomes qualificados como pacote.Arquivo.nome apontam um elemento direto.
  • Diretriz 20, equilibre compacto e compreensível. O documento é escrito uma vez e lido muitas, então clareza vem primeiro, sem prolixidade. Forma curta para o que se usa muito; para o raro, pode ser longa.
  • Diretriz 21, use o mesmo estilo em toda parte. Se uma sublinguagem agrupa com chaves e outra com parênteses, ninguém cria intuição. Ajuda também uma regra simples, como "toda palavra-chave é uma palavra só, em minúsculas".
  • Dilema da OCL embutida: adaptar a sintaxe dela ao estilo da hospedeira dá um estilo só; manter a OCL padrão deixa a OCL igual em todo lugar. O artigo pende para a padrão.
  • Diretriz 22, identifique convenções de uso. Nem tudo cabe na definição da linguagem (diretriz 11), e forçar layout pela ferramenta é rígido demais. Convenções descrevem regras que podem ser seguidas sem serem obrigatórias: maiúsculas nos nomes, atributos antes de métodos, formato dos comentários.
  • As Java Code Conventions são o exemplo do artigo: ninguém é obrigado pelo compilador a escrever nomes de classe com maiúscula, mas todo mundo escreve.
  • Pôr regra de estilo na gramática (o compilador recusa nome de variável com maiúscula). A diretriz 22 manda deixar isso como convenção.

Sintaxe abstrata (23–26): alinhar, ignorar o layout, dividir

Com layout significativo, espaço em branco vira significado.

As diretrizes da sintaxe abstrata pedem uma representação interna que acompanhe a concreta, que não dependa do layout e que permita dividir o sistema em partes com interfaces.

  • Diretriz 23, alinhe sintaxe abstrata e concreta. A estrutura interna deve seguir de perto o texto, para facilitar processar, transformar e reimprimir o modelo. Três princípios:
  • Primeiro, o que é diferente na concreta tem notação abstrata diferente. Segundo, elementos com significado parecido podem reaproveitar um conceito abstrato (em geral por subclasse), uma decisão mais de semântica que de estrutura. Terceiro, a notação abstrata depende só do elemento, nunca do contexto em que ele aparece.
  • Mau exemplo do artigo: na OCL, = é atribuição dentro do let e igualdade nas expressões. Mesmo texto, significados diferentes, decididos pelo contexto.
  • Quem usa um motor de transformação acaba vendo a estrutura interna. O alinhamento deixa o domínio aparecer na linguagem com pouco viés de implementação.
  • Diretriz 24, prefira layout que não afete a tradução da concreta para a abstrata. Um bom layout ajuda a ler, mas não deve mudar o significado. Espaços, tabulações e quebras de linha mudam de editor para editor e são difíceis de enxergar.
  • No gráfico, o mau exemplo é o Stateflow: a posição das transições no desenho (a "semântica do meio-dia") muda a ordem em que elas são testadas e, portanto, o comportamento.
  • Diretriz 25, permita modularidade. Dividir um sistema em peças pequenas, definidas separadamente, é a técnica principal contra a complexidade (Parnas, 1972) e permite gerar código só da parte que mudou. A linguagem precisa de elementos para referenciar outros arquivos.
  • Diretriz 26, introduza interfaces. Uma interface diz o que uma parte oferece ou precisa e esconde como ela faz. Dá para trocar a implementação sem afetar o resto, desde que a interface fique igual. Exemplos: modificadores de visibilidade do Java, portas em diagramas de estrutura composta.
  • No desenho, a mesma sequência de caracteres com 4 espaços a menos antes de z = 2 tira o comando de dentro do se. Numa linguagem com chaves, se (x > 0) { y = 1; } z = 2; diz isso com símbolos visíveis.
  • Python segue a indentação e funciona, então a diretriz 24 está errada? O artigo é uma recomendação para DSLs: o custo é o cuidado extra com editores e trabalho em grupo, não a impossibilidade.

Quando as diretrizes brigam

Cabo de guerra entre reuso e liberdade.

As diretrizes se contradizem, e cada uma pesa diferente conforme o tamanho dos modelos, o uso da linguagem e o custo de aplicá-la. O artigo trata as 26 como propostas a considerar, não como lei.

  • O conflito maior: reaproveitar (5, 6 e 7) ou criar do zero. Reaproveitar economiza tempo, já traz alguma qualidade e cumpre de graça diretrizes como estilo único (21) e modularidade (25).
  • Mas reaproveitar engessa: adaptar a linguagem herdada pode ser difícil ou impossível, e corrigir nela uma diretriz que não foi seguida pode exigir mudança grande.
  • Reaproveitar também briga com a diretriz 14: se nenhuma linguagem pronta lembra a notação do domínio, não dá para atender as duas. E juntar várias linguagens traz estilos e sistemas de tipos diferentes.
  • Do zero você ganha liberdade, mas paga sintaxe concreta e abstrata, condições de contexto e sistema de tipos. Escolher entre os dois caminhos é das decisões mais importantes.
  • Tamanho dos modelos: numa linguagem de configuração, com modelos de poucas linhas, organização em arquivos (19) e modularidade (25) quase não valem; para sistemas grandes, valem muito.
  • Uso: numa DSL só de documentação, evitar elementos ineficientes (13) não faz sentido; numa que vira código em execução, importa muito.
  • Custo: permitir comentários (18) e elementos distinguíveis (16) é barato; referências entre arquivos (19) exigem resolução de nomes e tabela de símbolos. Em DSL pequena, o caro pode ficar de fora.
  • Só que DSLs crescem, e pôr modularidade numa linguagem que já cresceu custa mais do que no começo. Analisar uso e usuários cedo (1 e 2) evita esse custo.

O que uma especificação de linguagem traz

Uma camada por fase do compilador.

Especificar uma linguagem é escrever, sem deixar dúvida, o que é um programa válido e o que ele significa. A especificação tem uma camada para cada fase do compilador: léxico, sintaxe e semântica, mais exemplos.

  • Esta seção é complemento: o vídeo e o artigo falam de projetar a linguagem, não de como escrever o documento. Confira a notação na seção 2.4 do livro da Melo.
  • Léxico: a lista de tokens, cada um com seu padrão (uma expressão regular), as palavras-chave e o que é descartado (espaços, comentários).
  • Sintaxe: a GLC, escrita em BNF ou EBNF, cujos terminais são os tipos de token. Ela não pode ser ambígua; em expressões, use um nível por operador.
  • Semântica: o que cada construção faz e as regras que a gramática não confere, como tipos compatíveis e "declarar antes de usar" (aula 07). Em geral fica em texto, uma regra por linha.
  • Exemplos: programas válidos e um programa com cada tipo de erro (léxico, sintático, semântico). Eles servem de teste para o compilador depois.
  • A EBNF é uma BNF com atalhos para repetição e opção. Ela não gera nenhuma linguagem que a BNF não gere: cada atalho vira regras comuns.
{ x } zero ou mais x
[ x ] x opcional
( a | b ) a ou b, agrupado
"se" terminal escrito como está
  • Nesta aula, variável em minúsculas (expr), token em maiúsculas (INTEIRO), texto fixo entre aspas e ; no fim de cada regra. Muita documentação e o ANTLR usam *, + e ? no lugar de { } e [ ], como nas expressões regulares.
  • EBNF: lista = item { "," item } ;. A mesma coisa em GLC: L → I R, R → , I R | ε. A chave virou uma variável nova que se repete ou some.
  • EBNF: se = "se" "(" expr ")" bloco [ "senao" bloco ] ;. Em GLC, o opcional vira duas alternativas: SE → se ( E ) B | se ( E ) B senao B.
  • A EBNF não é mais poderosa que a BNF; é só mais curta.
  • Escrever a regra semântica dentro da gramática ("o identificador tem de ter sido declarado"). A GLC não consegue conferir isso; vai para a seção de semântica.

Especificando uma linguagem pequena: a Mini

Um exemplo autoral de ponta a ponta: a Mini, uma linguagem pequena para estudantes escreverem contas e decisões. Cada parte da especificação aplica uma ou mais diretrizes. A Figura 2 monta o documento passo a passo.

  • A Mini não é a linguagem do projeto. Os tokens de expressão seguem a gramática da aula 08 para você ver como uma especificação cresce a partir dela.
  • Propósito (1–3): quem escreve são estudantes; o uso é traduzir para Python e rodar; tudo o que não serve a contas e decisões fica de fora.
  • Realização (4–7): textual, porque é rápida de construir com ANTLR. Expressões e comandos copiam a forma de C e Python (6), e os tipos são só inteiro e booleano, como em qualquer linguagem (7).
  • Conteúdo (8–13): atribuição, se/senao, enquanto, escreva e expressões. Um comando de repetição só (12).
  • Sintaxe concreta (14–22): + soma, ; termina comando, comentário //, palavras-chave em minúsculas. Igualdade é == e atribuição é =, dois tokens diferentes (23).
  • Blocos entre chaves: a indentação não muda nada (24) e cada senao fica preso ao se do seu bloco, sem a dúvida do if/else da aula 08.
programa = { comando } ;
comando = atribuicao | se | enquanto | escreva ;
atribuicao = IDENT "=" expr ";" ;
se = "se" "(" expr ")" bloco [ "senao" bloco ] ;
enquanto = "enquanto" "(" expr ")" bloco ;
escreva = "escreva" "(" expr ")" ";" ;
bloco = "{" { comando } "}" ;
expr = soma [ OPREL soma ] ;
soma = termo { OPSOMA termo } ;
termo = fator { OPMUL fator } ;
fator = "(" expr ")" | IDENT | INTEIRO | "verdadeiro" | "falso" ;
  • IDENT é [a-z][a-z0-9_]* menos as palavras-chave; INTEIRO é [0-9]+; OPREL é == != < <= > >=; OPSOMA é + -; OPMUL é * /. Espaços e comentários // … até o fim da linha são descartados.
  • Regras semânticas: variável só pode ser lida depois de receber valor; a condição de se e de enquanto tem de ser booleana; + - * / e < > só entre inteiros; == e != entre dois valores do mesmo tipo.
  • Válido: n = 5; f = 1; enquanto (n > 1) { f = f * n; n = n - 1; } escreva(f); escreve 120.
  • Erro léxico: x = 2 @ 3; (@ não é token). Erro sintático: x = 3 + ;. Erro semântico: escreva(y); sem atribuir y antes, ou se (3) { … }.
  • A gramática aceita se (1 + 2) { … }. Rejeitar condição que não é booleana é tarefa da semântica, não da GLC.
  • Na Mini, verdadeiro casa com o padrão de IDENT; a palavra-chave precisa ter prioridade, como na aula 07.

Treino: exercícios autorais

Exercícios autorais, não do professor, sobre o vídeo, o artigo e a especificação. Resolva antes de abrir a resposta; ela é uma solução possível, não a única.

1 · Classifique como DSL ou propósito geral: SQL, C, CSS, Python, expressão regular, Makefile.
Uma resposta

DSL: SQL (consultas), CSS (aparência de páginas), expressão regular (padrões de texto), Makefile (como compilar um projeto). Propósito geral: C e Python.

2 · Uma DSL tem repita 3 vezes { … } e também enquanto (i < 3) { … }. Que diretriz isso arrisca e como você defenderia manter os dois?
Uma resposta

Diretriz 12 (redundância conceitual): dois jeitos de repetir. A defesa é a 17: se repetir um número fixo de vezes é muito comum na área, a forma curta é açúcar que compensa, como o for aprimorado do Java.

3 · Numa linguagem, x = 3 atribui fora de um teste e compara dentro dele. Qual diretriz é quebrada e como corrigir?
Uma resposta

Diretriz 23: a notação abstrata depende do contexto, como o = da OCL. Corrija com dois tokens, = para atribuir e == para comparar, que viram nós diferentes na árvore.

4 · Um time quer uma DSL para analistas financeiros escreverem regras de crédito. Faça as perguntas da diretriz 2 e diga uma decisão que depende das respostas.
Uma resposta

Quem escreve as regras (analistas)? Quem revisa (risco, jurídico), e quando (antes de cada mudança)? Quem usa os modelos, e para quê (o sistema, para aprovar crédito; auditoria, para explicar a decisão)? Se a auditoria lê, a linguagem precisa de notação descritiva e comentários (15 e 18); se o sistema executa, nada pode ficar subespecificado (1).

5 · Escreva em EBNF uma lista de parâmetros como (a, b, c), que também pode ser (). Depois passe para GLC.
Uma resposta

EBNF: params = "(" [ IDENT { "," IDENT } ] ")" ;. GLC: P → ( ) | ( L ), L → id R, R → , id R | ε.

6 · Na Mini, classifique o erro: escreva(1 < verdadeiro);, enquanto n > 0 { n = n - 1; } e x = 10 # 2;.
Uma resposta

Semântico (< só entre inteiros); sintático (faltam os parênteses da condição); léxico (# não é token).

7 · Desenhe a sintaxe abstrata de se (a > 0) { b = a * 2; } e diga o que da sintaxe concreta não aparece nela.
Uma resposta

Raiz Se com dois filhos: a condição Maior(a, 0) e o bloco com Atribuição(b, Mult(a, 2)). Somem os parênteses, as chaves, o ; e as palavras se e =, que viraram o tipo dos nós.

8 · Para uma DSL de configuração com arquivos de 10 linhas, vale implementar import entre arquivos (diretriz 19)?
Uma resposta

Provavelmente não: modelos pequenos quase não ganham com isso, e referências entre arquivos exigem resolução de nomes e tabela de símbolos. A ressalva do artigo: se a DSL tende a crescer, pôr isso depois custa mais.

Uma boa resposta cita o número da diretriz e diz o que a decisão custa para quem usa a linguagem.
